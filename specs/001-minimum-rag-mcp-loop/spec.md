# Feature Specification: Minimum RAG MCP Loop

**Feature Branch**: `001-minimum-rag-mcp-loop`

**Created**: 2026-08-26

**Status**: Draft

**Input**: User description: "建立首个端到端闭环，让单用户通过 Web 管理项目与公共知识，上传 Markdown 和 Java 材料，并让 Claude Code 与 DeepSeek Harness 通过只读 MCP 获得可追溯的项目证据。"

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 建立可检索的项目知识 (Priority: P1)

用户通过浏览器创建项目知识域，上传 Markdown 文档和 Java 源代码，查看处理状态，并在处理成功后获得一个可检索的知识版本。

**Why this priority**: 没有可维护、可发布的项目知识，后续 MCP 检索无法产生用户价值。

**Independent Test**: 创建一个项目，上传一份 Markdown 文档和一组 Java 文件，确认每个知识源显示明确状态，并确认发布版本声明 Dense 检索能力。

**Acceptance Scenarios**:

1. **Given** 系统中没有项目，**When** 用户创建项目并上传受支持材料，**Then** 系统展示从接收到可检索或失败的完整状态。
2. **Given** 材料包含密码、Token 或 API Key 值，**When** 系统建立检索内容，**Then** 凭据值被类型化占位符替换，而变量名、代码结构和来源位置保留。
3. **Given** 某个知识源处理失败，**When** 用户查看详情并发起重试，**Then** 系统保留失败原因并创建可追踪的重试运行。
4. **Given** 新版本尚未成功发布，**When** 用户或 Agent 检索该项目，**Then** 已发布旧版本继续可用，未完成版本不参与检索。

---

### User Story 2 - 外部 Agent 获取项目证据 (Priority: P1)

用户在 Claude Code 或 DeepSeek Harness 中工作时，外部 Agent 可以针对一个或多个显式项目查询知识，并获得可直接使用、来源可定位的证据。

**Why this priority**: 这是系统对用户的核心价值，也是验证知识管理、检索与 MCP 能否形成闭环的最短路径。

**Independent Test**: 分别从 Claude Code 和 DeepSeek Harness 调用主检索 Tool，验证相同查询获得符合契约的证据，并能定位到原始 Markdown 章节或 Java 文件与符号。

**Acceptance Scenarios**:

1. **Given** 一个已发布的项目知识版本，**When** Agent 携带唯一项目作用域查询项目事实，**Then** 系统只返回该作用域允许的证据。
2. **Given** 请求没有项目作用域，**When** Agent 发起项目检索，**Then** 系统拒绝全库搜索并返回可纠正的作用域错误。
3. **Given** 请求显式包含两个项目，**When** Agent 发起跨项目查询，**Then** 系统只在这两个项目内检索并保留每条证据的项目身份。
4. **Given** 查询涉及已登记的公共知识，**When** 系统返回项目和公共证据，**Then** 两类证据的知识域身份清晰且公共证据不覆盖冲突的项目证据。

---

### User Story 3 - 按需展开证据 (Priority: P2)

外部 Agent 在核心证据不足以完成当前推理时，可以通过证据 ID 和显式项目作用域读取完整 Chunk、父级章节、所属类或相邻代码。

**Why this priority**: 主检索响应必须保持精简，同时不能阻止 Agent 获取完成设计或编码所需的局部细节。

**Independent Test**: 从主检索结果选择一个证据 ID，调用证据展开 Tool，验证返回内容与来源版本一致，并验证越权作用域不能读取该证据。

**Acceptance Scenarios**:

1. **Given** 主检索返回一个项目证据 ID，**When** Agent 使用相同项目作用域展开证据，**Then** 系统返回完整内容和父级定位。
2. **Given** 证据不属于请求中的项目作用域，**When** Agent 尝试展开，**Then** 系统不返回正文并报告作用域不匹配。
3. **Given** 证据属于公共知识域且主检索已将其返回，**When** Agent 携带原项目作用域和公共证据 ID 展开，**Then** 系统验证该证据来自允许的公共检索路径后返回内容。
4. **Given** 证据引用的版本已被清空或撤销，**When** Agent 尝试展开，**Then** 系统返回不可用状态而不是其他版本的替代内容。

---

### User Story 4 - 管理知识生命周期 (Priority: P2)

用户可以查看项目和公共知识源、删除单个知识源、清空知识域，并明确知道这些操作何时停止检索及何时完成。

**Why this priority**: 用户维护是首期唯一知识更新方式，必须能够移除错误或过期材料。

**Independent Test**: 删除一个已发布知识源并清空一个测试知识域，验证它们先停止参与新检索，再完成派生数据删除，且其他项目不受影响。

**Acceptance Scenarios**:

1. **Given** 一个已发布知识源，**When** 用户删除该知识源，**Then** 它停止参与新检索且删除进度可见。
2. **Given** 一个包含多个知识源的项目，**When** 用户确认清空，**Then** 该项目停止检索并异步删除派生数据。
3. **Given** 两个独立项目，**When** 用户清空其中一个，**Then** 另一个项目和公共知识域保持可检索。

### Edge Cases

- 上传空文件、损坏文件、伪装扩展名或不受支持格式时，系统必须拒绝处理并说明原因。
- 重复上传内容哈希相同的材料时，系统必须避免创建不可区分的重复有效版本。
- Java 文件无法形成完整语法树时，系统必须报告降级或失败，不得伪造符号边界。
- 发布过程中部分派生数据写入失败时，未完成版本不得参与检索。
- 同一 Agent 的多个会话或多个 Agent 并发查询时，请求状态和项目作用域不得互相污染。
- 公共证据与项目证据冲突时，两者必须并列返回并标明知识域。
- 返回内容达到服务端装箱上限时，系统必须保留最高相关的可定位证据，并提供可展开的证据 ID。
- 删除或清空操作重复提交时，结果必须保持幂等。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统 MUST 提供浏览器可访问的管理入口，用于管理项目知识域和公共知识域。
- **FR-002**: 用户 MUST 能够创建、查看和识别项目知识域与公共知识域。
- **FR-003**: 系统 MUST 为每个知识域分配稳定且唯一的知识域标识。
- **FR-004**: 用户 MUST 能够上传 Markdown 文档和 Java 源代码材料。
- **FR-005**: 系统 MUST 为每个上传知识源记录来源、内容哈希、版本和处理状态。
- **FR-006**: 系统 MUST 在检索表示中将明确的凭据值替换为类型化占位符，同时保留字段名、结构和来源位置。
- **FR-007**: 系统 MUST 对 Markdown 使用章节感知切片，对 Java 使用符号感知切片，并保留父子上下文关系。
- **FR-008**: 系统 MUST 允许发布声明 Dense 检索能力的知识版本，未发布版本 MUST NOT 参与检索。
- **FR-009**: 新版本发布失败时，系统 MUST 保持最近一个已发布版本可检索。
- **FR-010**: 用户 MUST 能够查看处理失败原因并重试失败的知识源。
- **FR-011**: 用户 MUST 能够删除单个知识源并清空指定知识域。
- **FR-012**: 删除和清空 MUST 先停止目标内容参与新检索，再完成派生数据清理。
- **FR-013**: 系统 MUST 提供一个只读主检索能力，接受查询、显式项目作用域和可选任务上下文。
- **FR-014**: 项目检索缺少显式项目作用域时，系统 MUST 拒绝默认全库搜索。
- **FR-015**: 系统 MUST 支持显式单项目和多项目作用域，且不得返回作用域外的项目证据。
- **FR-016**: 系统 MAY 在查询涉及已登记公共能力时返回公共证据，但 MUST 保留公共域身份并暴露与项目证据的冲突。
- **FR-017**: 主检索结果 MUST 包含完成状态、核心证据、证据 ID、来源版本、来源位置、相关性信息和明确缺口。
- **FR-018**: 系统 MUST 提供只读证据展开能力，并要求证据 ID 与显式项目作用域。
- **FR-019**: 证据展开 MUST 验证项目证据属于请求作用域；公共证据 MUST 验证其来自该项目查询允许的公共检索路径。
- **FR-020**: 已撤销、删除或未发布版本的证据 MUST NOT 被其他版本内容静默替代。
- **FR-021**: 规范结果 MUST 以可校验的结构化内容返回；兼容文本 MUST 由同一规范结果确定性生成。
- **FR-022**: 两个核心检索能力 MUST 能被 Claude Code 和 DeepSeek Harness 调用，且核心流程 MUST NOT 依赖 Resources 或 Tasks。
- **FR-023**: 同一后端 MUST 隔离不同 Agent、不同会话和并发请求的运行状态。
- **FR-024**: 系统 MUST 建立可重复执行的固定评测集，并记录首个 Dense 检索基线。
- **FR-025**: 系统 MUST 记录每次检索的请求标识、知识作用域、完成状态和证据引用，以支持问题回溯。
- **FR-026**: 当前未认证的管理与 MCP 服务 MUST 默认仅允许本机访问。

### Key Entities *(include if feature involves data)*

- **Knowledge Scope**: 项目域或公共域的统一身份，包含稳定标识、类型和有效状态。
- **Project**: 用户工作的项目身份，可关联一个项目知识域及可识别的别名或仓库路径。
- **Knowledge Source**: 用户上传的原始材料及其哈希、格式、来源和生命周期状态。
- **Knowledge Version**: 一个可发布或已发布的知识快照，声明当前可用检索能力。
- **Chunk**: 从知识源产生的结构化检索单元，包含父子关系和来源定位。
- **Evidence**: 可由 MCP 返回和展开的版本化检索结果。
- **Processing Run**: 一次上传处理或重试运行，包含阶段、状态和失败原因。
- **Retrieval Run**: 一次独立检索调用的状态及证据引用。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 用户能够仅通过浏览器完成项目创建、Markdown/Java 上传并看到最终处理状态。
- **SC-002**: 验收测试集中的所有项目检索均不返回显式作用域之外的项目证据。
- **SC-003**: 验收测试集中的所有成功证据均可定位到确定的知识源版本和内容位置。
- **SC-004**: 验收测试集中的所有 Tool 成功响应均通过其规范输出 Schema 校验。
- **SC-005**: Claude Code 与 DeepSeek Harness 均能完成主检索和证据展开的端到端调用。
- **SC-006**: 包含测试凭据的验收材料中，真实凭据值不会出现在检索索引或 MCP 证据正文，配置字段名和结构仍可检索。
- **SC-007**: 删除或清空一个知识域后，新的检索不再返回该域的已删除内容，其他知识域结果不受影响。
- **SC-008**: 同一后端在并发验收场景中不会发生请求状态、证据或项目作用域串扰。
- **SC-009**: 固定评测集能够重复产生 Dense 检索的 Recall@K、MRR、nDCG 和 P50/P95 延迟基线。
- **SC-010**: 无可靠证据、部分证据和系统失败三类情况均返回可区分、可操作的状态，不以生成内容填补缺口。

## Assumptions

- 当前面向单用户，本 Feature 不提供登录、角色和权限体系。
- 管理端与 MCP 服务默认运行在用户控制的本机环境。
- 本 Feature 使用单 Writer 实例；Reader 模式和多实例硬化属于后续 Runtime Hardening Feature。
- 原始上传文件由 Writer 本地保存；共享数据库保存 Reader 检索所需的 Chunk 正文与来源定位。
- 本 Feature 只建立 Dense 检索基线，不包含 BM25、Rerank、Graph RAG 或三个检索 Agent。
- 公共知识参与检索必须由查询与已登记公共能力的关联触发，不默认注入所有公共内容。
- 用户负责确认上传材料拥有合法使用权限。
