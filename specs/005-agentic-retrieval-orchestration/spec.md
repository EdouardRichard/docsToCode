## 对照对象（基线）

本 Feature 的对照评测对象为 **确定性检索基线**，即 001 建立、经 002/003/004 增强的确定性编排路径（确定性的项目作用域过滤、Dense/Sparse/图召回、RRF/DBSF 融合、Cross-Encoder Rerank、确定性证据排序与上下文装箱，无三 Agent 介入，蓝图 §12 末段）。

首要对照为 **001 Markdown/Java 确定性基线**（Feature `001-minimum-rag-mcp-loop`），其基线数据记录于 `eval/baseline_report.json`：

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 复杂与多跳查询被拆解后获得更完整证据 (Priority: P1)

外部 Agent（ChatGPT App、DeepSeek Harness、Claude Code）以跨多个子问题或多个代码结构的复杂查询发起检索（例如"哪些服务调用了 `UserService#validateToken` 且 validateToken 自身依赖什么"这一 Java 调用图多跳查询，或"`orders.user_id` 外键如何关联 `users` 表、orders 暴露哪些字段"这一 DDL 外键多跳查询）。查询规划 Agent 识别查询意图、拆解检索子问题、选择所需检索信号与关系方向，并行执行检索路径后返回覆盖完整意图的证据，而非仅返回首个语义最相似的单条证据。确定性基线在不含规划 Agent 时按单次语义匹配返回，会遗漏结构性多跳覆盖。

**Why this priority**: 查询规划 Agent 是 005 相对确定性基线的核心增量之一。多跳结构查询恰由输入材料中的 Java 调用图 / DDL 外键语料与混合检索代码语料承载，是 Agent 拆解价值最直接的验证场景，也是蓝图 §9 信号 6（复杂冲突或多跳问题中的 LLM 语义判断）的运行时落点。

**Independent Test**: 在新增 Agent 受益查询批次（多跳查询子集）上分别运行 Agent 编排路径与确定性基线，验证 Agent 路径在该子集的 Recall@K 高于确定性基线，且每条查询的拆解子问题、所选检索信号与关系方向被记录可追溯。

**Acceptance Scenarios**:

1. **Given** 一个已发布且声明可用检索能力的知识版本（含 Java 调用图 / DDL 外键语料），**When** Agent 携带显式项目作用域发起多跳结构查询，**Then** 查询规划 Agent 将其拆解为可追溯的子问题并选择 Dense/Sparse/图扩展信号，并行检索后返回覆盖各子问题的证据。
2. **Given** 查询只含单一意图（无可拆解子问题），**When** 查询规划 Agent 处理该查询，**Then** Agent 仍输出检索信号与过滤条件，路径退化为确定性单次检索，不引入超出信号选择的开销。
3. **Given** 查询引用的精确符号只存在于作用域外项目，**When** Agent 仅携带本项目作用域查询，**Then** 系统不返回作用域外证据，跨项目泄漏事件数为零（查询规划与检索信号选择均受作用域约束）。
4. **Given** 查询涉及已登记公共能力，**When** 查询规划 Agent 判断需要公共知识，**Then** 公共证据与项目证据分别召回并保留知识域身份，公共证据不覆盖冲突的项目证据。

### User Story 2 - 证据缺口触发有界补充检索 (Priority: P1)

当首轮检索后存在可验证证据缺口（期望证据未进入 Top-K、某子问题未被覆盖、或存在未解决冲突）时，证据分析 Agent 输出结构化覆盖度/缺口/冲突判断，确定性状态机在仍处于最大检索轮次内时执行补充检索，将首轮遗漏的可靠证据纳入最终结果，而非止步于本可改进的部分答案。缺口判断、补充检索查询与每轮召回均追加进入证据账本，可解释"为何返回这条证据"。

**Why this priority**: 补充检索是蓝图 §23.4.5 对 005 的明确命名项之一，也是相对确定性单轮基线最直接的召回增量。证据分析 Agent 的结构化缺口判断与确定性控制器的继续/返回决策，是蓝图 §14 混合充分性机制的运行时实现。

**Independent Test**: 构造首轮可验证缺口查询（期望证据在首轮 Dense/Sparse 召回中排名靠后），运行 Agent 编排路径，验证补充检索轮次召回缺失证据、最终 Recall@K 高于确定性单轮基线，且缺口判断与补充检索轮次在账本中可追溯。

**Acceptance Scenarios**:

1. **Given** 首轮检索后某子问题未被覆盖，**When** 证据分析 Agent 输出该缺口且迭代未达上限，**Then** 确定性控制器触发补充检索，查询规划 Agent 携带缺口上下文重新生成补充检索查询，补充召回的证据追加进入账本并参与最终选择。
2. **Given** 补充检索已达最大检索轮次且仍存在缺口，**When** 系统进入返回阶段，**Then** 结果为 `partial` 并携带已验证证据、未覆盖问题、冲突与失败路径（蓝图 §14），不以生成内容填补缺口。
3. **Given** 证据分析 Agent 输出"无缺口"，**When** 确定性控制器判定无需继续，**Then** 系统直接进入上下文编排，不执行多余补充检索轮次。
4. **Given** 项目证据与公共证据存在版本/来源冲突，**When** 证据分析 Agent 识别冲突，**Then** 系统并列返回两类证据并标明知识域身份，不臆造裁决；冲突标记进入账本可追溯（宪法原则 III）。

### User Story 3 - 最终上下文去重、保多样、可解释 (Priority: P1)

最终返回的证据经上下文编排 Agent 组织为外部 Agent 可直接消费的上下文：消除重复内容、保留来源多样性、按需补充父级上下文范围、输出符合节点 Schema 的编排结果。每条返回证据在追加式证据账本中可定位到其检索查询、检索器、得分、版本、来源与产生轮次，使外部 Agent 能解释"为何返回这条证据"。Agent 可引用、评价或筛选证据，但不得覆盖原始检索记录。

**Why this priority**: 上下文编排与追加式证据账本是蓝图 §23.4.5 对 005 的明确命名项；证据可定位是宪法原则 IV（Locatable Evidence）与蓝图 §13 的硬性要求。相对 001 已有的检索运行追踪，005 的增量是"追加式、不覆盖"的账本结构与上下文编排 Agent 的去重/多样/父级补充判断。

**Independent Test**: 对返回多条重叠证据的查询运行 Agent 路径，验证最终上下文无重复证据、保留至少一条来自不同来源的证据、每条证据携带账本引用可解析至检索查询/检索器/得分/版本/来源/轮次，且账本原始记录未被任何 Agent 改写。

**Acceptance Scenarios**:

1. **Given** 多条检索路径召回内容重叠的证据，**When** 上下文编排 Agent 组织最终上下文，**Then** 重复内容被消除、来源多样性被保留、最终上下文符合节点 Schema。
2. **Given** 某证据需父级上下文才能被外部 Agent 正确使用，**When** 上下文编排 Agent 决定父级补充范围，**Then** 父级上下文按需纳入且不超出最终上下文装箱上限。
3. **Given** 任一返回证据，**When** 外部 Agent 或回溯检查解析其账本引用，**Then** 可定位到检索查询、检索器、得分、版本、来源与产生轮次，且原始记录未被覆盖。
4. **Given** 检索返回超过最终上下文装箱上限的证据，**When** 上下文编排 Agent 装箱，**Then** 保留最高相关可定位证据，并为被截断证据提供可展开的证据 ID（沿用 001 超量截断策略）。

### User Story 4 - Agent 编排经对照评测证明收益后进入默认检索路径 (Priority: P2)

Agent 编排在固定评测集（含 001 Markdown/Java 11 条基线与新增 Agent 受益查询批次）上与确定性检索基线对照评测，只有在证明可度量收益（Agent 受益子集 MRR/nDCG 提升、Recall@K 不下降、001 基线非回归）且未违反任何硬性验收指标（跨项目泄漏为零、Schema 合法率 100%、来源可定位率 100%）后，才进入默认检索路径；未达阈值则 Agent 编排作为可选检索路径保留、不进入默认路径。

**Why this priority**: 这是宪法原则 X（评测驱动优化）与蓝图 §24.3 对所有增强（含三 Agent）的强制闸口。它是进入生产的门禁而非用户可见价值本身，故为 P2；但其结果决定 US1–US3 是否进入默认路径。

**Independent Test**: 运行对照评测，产出逐查询的确定性基线排名与 Agent 排名、Agent 判断（拆解子问题、缺口分析、补充检索轮次、上下文编排决策）与账本引用的对照报告，验证通过/未通过判定与默认路径决策，并可重复执行。

**Acceptance Scenarios**:

1. **Given** 固定评测集与确定性基线报告，**When** 系统在同一评测集上运行 Agent 编排路径，**Then** 产出含 Recall@K、MRR、nDCG、P50/P95 延迟与模型成本的 Agent 编排报告，并与 001 `baseline_report.json` 及确定性增强路径报告逐项对照。
2. **Given** Agent 受益子集指标达阈值且硬性指标全过，**When** 评估判定通过，**Then** Agent 编排进入默认检索路径。
3. **Given** Agent 受益子集指标未达阈值，**When** 评估判定未通过，**Then** Agent 编排作为可选检索路径保留、不进入默认路径，确定性路径继续作为默认。
4. **Given** 同一环境连续两次运行，**When** 重跑对照评测，**Then** 非延迟指标在容差内一致、延迟指标标注为环境敏感（沿用 001/002/004 可重复性约定）。

### Edge Cases

- 当某 Agent 结构化输出未通过 Schema 校验时，确定性控制器 MUST 将其视为降级判断并回退到该角色的确定性等价行为，状态机 MUST NOT 因无效 Agent 输出阻塞确定性路径（蓝图 §15、宪法原则 VI）。
- 当补充检索达最大检索轮次仍有缺口时，系统 MUST 返回 `partial` 并携带已验证证据、未覆盖问题、冲突与失败路径，不以生成内容填补缺口（蓝图 §14）。
- 当查询规划 Agent 判定查询为单一意图、无可拆解子问题时，路径 MUST 退化为确定性单次检索，不引入超出信号选择的开销。
- 当查询规划 Agent 在补充检索轮次中重新被调用但其结构化输出未通过 Schema 校验时，状态机 MUST 回退到沿用首轮拆解的原始子问题查询执行补充检索（确定性等价行为），不因查询规划 Agent 降级而阻塞补充检索路径（蓝图 §15、宪法原则 VI）。
- 当项目证据与公共证据冲突且无法裁决时，系统 MUST 并列返回两者并标明知识域身份，不臆造裁决；冲突标记进入账本可追溯（宪法原则 III）。
- 当检索内容含提示注入时，原始内容只进入证据字段，控制指令与证据内容使用结构化边界隔离，高风险片段从内部控制 Prompt 隔离但保留可审计来源，Agent 结构化输出 MUST 通过 Schema 校验（蓝图 §15）。
- 当某 Agent 节点超时时，状态机执行节点超时护栏；已有可靠证据时返回 `partial`，该 Agent 角色回退到确定性等价行为（蓝图 §19）。
- 当 Agent 编排被运行配置关闭或评估未通过阈值时，系统 MUST 回退到确定性检索路径并仍返回有效 `completion_status` 四态结果（蓝图 §14、§19）。
- 当多个请求并发携带不同 `project_scope` 时，LangGraph 状态与证据账本 MUST 按 `request_id`/`run_id` 隔离，不发生状态、证据或作用域串扰（蓝图 §21、沿用 001 SC-008）。
- 当 Agent 推理结果产生时，运行状态 MUST NOT 自动写回项目知识库（蓝图 §20）；运行状态使用 TTL，追踪配置 MUST 允许关闭查询正文与证据正文记录、只保留 ID/状态/耗时/错误。

## Requirements *(mandatory)*

### Functional Requirements

**三 Agent 角色与能力路由**

- **FR-001**: 系统 MUST 实现三个独立逻辑 Agent 角色：查询规划 Agent、证据分析 Agent 与上下文编排 Agent，职责对齐蓝图 §11.1/§11.2/§11.3（识别意图与拆解子问题、评估覆盖度与缺口/冲突、组织去重多样可消费上下文）。
- **FR-002**: 每个 Agent 角色的实际模型 MUST 由能力路由层选择，允许简单角色使用低延迟模型、复杂证据判断使用更强模型；系统 MUST NOT 绑定具体 LLM 供应商（蓝图 §11 末段、§18）；具体模型选择、Prompt 与置信度阈值留给 plan.md / research.md 决策。
- **FR-003**: 每个 Agent 的结构化输出 MUST 通过其节点专属 Schema 校验后才能影响状态机；未通过校验的输出 MUST 被降级处理，不得阻塞确定性路径（蓝图 §15、宪法原则 VI）。

**确定性状态机**

- **FR-004**: LangGraph MUST 管理状态机与节点流转，LangChain 提供模型、Prompt 与 Retriever 适配；状态跳转权属于确定性控制器，不属于 Agent；任一 LLM 判断 MUST NOT 成为状态机跳转的唯一裁决（蓝图 §12、宪法原则 VI）。
- **FR-005**: 状态机 MUST 实现蓝图 §12 的主状态流：接收并校验请求 → 解析项目作用域 → 查询规划 → 并行执行检索路径 → 融合与 Rerank → 证据分析 → 若存在缺口且仍在最大迭代范围内则执行补充检索 → 上下文编排 → MCP 响应序列化。补充检索轮次为有界循环：当证据分析 Agent（步骤 6）输出缺口判断且确定性控制器决定继续时，查询规划 Agent（步骤 3）携带缺口上下文重新被调用以生成补充检索查询，补充召回的候选重新进入步骤 4（并行检索）→ 5（融合与 Rerank）→ 6（证据分析），使每轮补充召回证据携带融合/Rerank 分数并经证据分析 Agent 重新评估覆盖度，直至无缺口或达最大检索轮次后进入步骤 8（上下文编排）；一个检索轮次 = 查询规划（补充）+ 检索 + 融合 + Rerank + 证据分析。
- **FR-006**: 状态机 MUST 强制护栏：最大检索轮次、每条检索路径候选数、Rerank 候选数、单来源最大证据数、节点超时与整个 Tool Call 超时、最终上下文装箱上限；护栏作为运行配置管理而非写死在协议契约中（蓝图 §12、§19）。005 固化默认值见 Assumptions（轮次默认 2/上限 3、节点超时默认 5s/上限 10s、装箱上限沿用 001 top_k ≤ 20、总超时 30s、每路召回与 Rerank 候选沿用 002 实现值、图扩展跳数沿用 004 默认 2/上限 3、候选预算沿用 004 默认 10/上限 20、图查询子超时沿用 004 默认 3s、单来源最大证据数默认 3/上限 5）。
- **FR-007**: 服务端固定护栏 MUST 始终生效；调用方提供的响应偏好只能作为提示，系统 MUST NOT 要求外部 Agent 提供剩余 Token（蓝图 §12）。

**追加式证据账本与公共状态**

- **FR-008**: 原始证据 MUST 使用追加式账本；Agent 可以引用、评价或筛选证据，但 MUST NOT 覆盖原始检索记录（蓝图 §13、宪法原则 IV）。
- **FR-009**: 每条证据记录 MUST 记录其检索查询、检索器、得分、版本、来源、产生轮次与所属子问题（`sub_problem_id`），使系统能解释"为何返回这条证据"（蓝图 §13）。
- **FR-010**: 类型化公共状态包络 MUST 携带请求与项目作用域、任务上下文、运行配置与模型能力要求、当前迭代与护栏状态、证据账本引用与追踪信息（蓝图 §13）。
- **FR-011**: Agent 运行状态 MUST NOT 自动进入向量库或写回项目知识库；运行状态使用 TTL（蓝图 §20）。
- **FR-012**: 追踪配置 MUST 允许关闭查询正文与证据正文记录，只保留 ID、状态、耗时与错误（蓝图 §20）。

**补充检索与证据充分性**

- **FR-013**: 证据分析 Agent MUST 输出结构化覆盖度、缺口与冲突判断（含未覆盖子问题标识）；确定性控制器 MUST 据此决定继续检索或进入返回阶段，不由 Agent 独占该决策；当决定继续时，缺口判断作为上下文输入查询规划 Agent 以生成补充检索查询（蓝图 §14、宪法原则 VI）。
- **FR-014**: 当存在缺口且迭代仍在最大检索轮次内时，状态机 MUST 令查询规划 Agent 携带缺口上下文重新生成补充检索查询后执行补充检索，并令召回候选重新进入融合、Rerank 与证据分析（循环步骤 3→4→5→6→7），使补充证据携带融合/Rerank 分数且覆盖度被重新评估；当达上限或无缺口时，MUST 进入上下文编排（蓝图 §12 第 7 步）。
- **FR-015**: 证据判断混合机制 MUST 由硬指标（有效来源数、Rerank 分数、版本有效性、项目作用域、未解决冲突）与证据分析 Agent 的结构化判断共同支撑，确定性控制器决定终态（蓝图 §14）。
- **FR-016**: `partial` 终态 MUST 携带已验证证据、未覆盖问题、冲突与失败路径，不得只返回模糊文本；四态 `complete`/`partial`/`no_evidence`/`failed` 沿用 001（蓝图 §14、宪法原则 III）。

**上下文编排**

- **FR-017**: 上下文编排 Agent MUST 基于已选证据组织外部 Agent 可消费的上下文，消除重复内容、保留来源多样性、决定父级上下文补充范围，并输出符合节点 Schema 的上下文编排结果，以独立追加式选择清单（`context_result_id` 引用 `ledger_entry_id`，decision ∈ {selected, truncated, deduped}）记录选中/截断/去重决策而不改写原始账本条目（蓝图 §11.3、§13）。
- **FR-018**: 最终上下文装箱 MUST 受最终上下文装箱上限约束；超量时保留最高相关可定位证据并为被截断证据提供可展开证据 ID（蓝图 §12、沿用 001 超量截断策略）。

**提示注入防护与数据控制分离**

- **FR-019**: 上传材料与检索内容 MUST 始终视为不可信数据；原始内容只进入证据字段；控制指令与证据内容 MUST 使用结构化边界隔离；检索文本 MUST NOT 直接控制状态机跳转、工具调用或模型权限（蓝图 §15、宪法原则 V）。
- **FR-020**: 可疑提示注入内容 MUST 被检测和标记；高风险片段 MUST 可从内部控制 Prompt 隔离但仍保留可审计来源；Agent 结构化输出 MUST 通过 Schema 校验（蓝图 §15）。

**作用域、隔离与硬性约束（继承宪法与蓝图）**

- **FR-021**: 项目知识检索 MUST 携带显式 `project_scope`；缺少显式作用域时 MUST 拒绝并不得回退到默认或全库搜索；无法唯一解析项目引用时 MUST 停止检索并返回候选项目列表（宪法原则 I、蓝图 §4.1、001 FR-014/FR-017）。
- **FR-022**: 跨项目泄漏 MUST 为零：任一检索结果、证据账本条目、图关系或 Chunk 不得从一个 `project_scope` 出现在另一项目的检索中，除非显式多项目 `project_scope` 请求（宪法硬约束、蓝图 §24.2）。
- **FR-023**: 每条对外返回证据 MUST 携带来源 ID、版本与位置，可定位到原始知识源版本与内容位置（Markdown 章节路径或 Java 全限定符号路径）；MCP 响应 MUST 不暴露内部数据库结构（宪法原则 IV、蓝图 §13、001 FR-017）。
- **FR-024**: 验收测试集中所有 Agent 编排检索 Tool 成功响应 MUST 100% 通过 `search_knowledge` 与 `get_evidence` 输出 Schema 校验；来源可定位率 MUST 为 100%（宪法硬约束、蓝图 §24.2）；005 不修改对外契约（宪法原则 VII、001 已确立）。
- **FR-025**: LangGraph 状态 MUST 按 `request_id` 与 `run_id` 隔离；系统 MUST NOT 保存全局活动项目或隐式会话状态；每个请求独立携带 `project_scope`（蓝图 §21.1、001 FR-023）。

**对照评测（001 确定性基线）**

- **FR-026**: 系统 MUST 在固定评测集（001 原 11 条 Markdown/Java 基线 + 002/004 扩充集 + 005 新增 Agent 受益查询批次）上运行 Agent 编排评测，产出 Recall@K、MRR、nDCG、P50/P95 延迟与模型成本指标，并与 001 `baseline_report.json`（Markdown/Java 11 条）及确定性增强路径报告（002 `hybrid_comparison_report.json`、004 图增强）逐项对照（蓝图 §23.4.5、§24.1、§24.3）。
- **FR-027**: Agent 受益查询批次 MUST 以输入材料（混合检索代码、Java 调用图 / DDL 外键语料）构造多跳结构查询、首轮可验证缺口查询与版本/来源冲突查询（新增 ≥ 6 条，多跳/缺口/冲突各 ≥ 2 条，含 ≥ 1 条中文查询）；新增批次仍遵循 001 的 AI 生成、人工审核、JSON 格式约定（蓝图 §24.1、沿用 001/002/004 评测集扩展约定）。
- **FR-028**: 对照评测 MUST 逐查询记录确定性基线排名与 Agent 编排排名、各 Agent 判断（拆解子问题、所选检索信号与关系方向、缺口/冲突判断、补充检索轮次、上下文编排决策）、各子路径（Dense/Sparse/图扩展/融合/Rerank）耗时与证据账本引用，使排名变化可解释（宪法原则 IV、蓝图 §13）。
- **FR-029**: Agent 编排 MUST 在固定评测集上证明相对确定性基线的可度量收益——Agent 受益子集 MRR/nDCG 相对提升达阈值（固化为本 Feature：≥3% 相对提升）、Recall@K 不下降、001 之 11 条 Markdown/Java 基线非劣（沿用 1% 相对容差，值在 research.md），且未违反任何硬性验收指标（泄漏为零、Schema 100%、定位 100%）后，才进入默认检索路径；未达阈值则 Agent 编排作为可选检索路径保留、不进入默认路径（宪法原则 X、蓝图 §24.3）。
- **FR-030**: 对照评测 MUST 在同一环境会话内先重跑确定性基线、再运行 Agent 编排路径，以保证延迟增量对照公平（沿用 002/004 延迟对照公平策略）；非延迟指标同时与 `baseline_report.json` 及确定性增强路径报告交叉验证。
- **FR-031**: 系统 MUST 记录每次 Agent 编排检索的请求标识、知识作用域、完成状态、各子路径耗时、各 Agent 判断与证据账本引用（含补充检索轮次），以支持问题回溯（蓝图 §13 证据账本，沿用 001/002/004 追踪）。
- **FR-032**: 系统 MUST 固化以下标识与状态枚举为契约：证据账本条目 `ledger_entry_id`（雪花 ID）、查询规划 Agent 拆解子问题以 `run_id` 内单调递增 `sub_problem_id` 标识、补充检索轮次以 `run_id` 内单调递增 `round_index` 标识、证据分析 Agent 覆盖度状态枚举 {covered, partial, uncovered} 与冲突类型枚举 {none, version_conflict, source_conflict, domain_conflict}、上下文编排结果以 `run_id` 内稳定 `context_result_id` 标识及其追加式选择清单（decision 枚举 {selected, truncated, deduped}）、Agent 角色标识 {query_planner, evidence_analyst, context_orchestrator}，使账本引用与判断状态可追溯、可校验（蓝图 §13、宪法原则 IV）。
- **FR-033**: 查询规划 Agent MUST 可选择图扩展的关系方向子集（如 `calls`+`called_by`、`fk_references`+`fk_referenced_by`）与跳数上限（在 004 的 1~3 跳护栏内）；该选择经节点 Schema 校验后生效，未通过校验或 Agent 编排关闭时 MUST 回退到 004 的确定性双向成对默认（蓝图 §11.1、§12、宪法原则 VI、004 FR-007）。图扩展跳数、候选预算与查询子超时沿用 004 固化值（跳数默认 2/上限 3、候选预算默认 10/上限 20、子超时 3s），可由运行配置覆盖但不得超上限。

### Key Entities *(include if feature involves data)*

- **Agent 角色（Agent Role）**: 三独立逻辑角色之一（查询规划 / 证据分析 / 上下文编排），模型由能力路由选择，结构化输出经节点 Schema 校验，不拥有状态跳转权（蓝图 §11）。
- **公共状态包络（Public State Envelope）**: 类型化状态，携带请求与项目作用域、任务上下文、运行配置与模型能力要求、当前迭代与护栏状态、证据账本引用与追踪信息；按 `request_id`/`run_id` 隔离（蓝图 §13、§21）。
- **节点专属 Schema（Node-specific Schema）**: 各状态机节点的输入/输出契约；Agent 结构化输出据此校验（蓝图 §13、§15）。
- **证据账本条目（Evidence Ledger Entry）**: 追加式记录，稳定标识为雪花 ID（`ledger_entry_id`），含检索查询、检索器、得分、版本、来源、产生轮次（`round_index`）与所属子问题（`sub_problem_id`）；Agent 可引用/评价/筛选但不得覆盖（蓝图 §13）。
- **缺口/冲突判断（Gap/Conflict Judgment）**: 证据分析 Agent 的结构化输出：覆盖度状态枚举 {covered, partial, uncovered}、冲突类型枚举 {none, version_conflict, source_conflict, domain_conflict}、是否需要补充检索及未覆盖子问题标识；确定性控制器消费，缺口判断作为上下文输入查询规划 Agent 以生成补充检索查询（蓝图 §11.2、§14）。
- **补充检索轮次（Supplementary Retrieval Round）**: 由可验证缺口触发、受最大检索轮次约束的追加检索迭代；每轮由查询规划 Agent 携带缺口上下文重新生成补充检索查询后执行，追加进入证据账本（蓝图 §12 第 7 步）。
- **上下文编排结果（Context Orchestration Result）**: 上下文编排 Agent 的节点 Schema 输出：去重、保多样、按需父级补充的证据选择；稳定标识为 `context_result_id`（run_id 内），通过追加式选择清单（引用 `ledger_entry_id`，decision ∈ {selected, truncated, deduped}）记录选择决策而不改写原始账本条目，供 MCP 响应序列化（蓝图 §11.3、§13）。
- **Agent 编排检索运行（Agentic Retrieval Run）**: 使用三 Agent 编排路径的检索运行，记录拆解子问题、信号选择、缺口判断、补充轮次与账本引用；与 001 确定性 Retrieval Run 对照（蓝图 §13、§23.4.5）。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 在固定评测集的"Agent 受益"查询子集（多跳结构、首轮缺口、冲突查询）上，Agent 编排路径的 MRR 与 nDCG 均值相对确定性增强基线（002 `hybrid_comparison_report.json` + 004 图增强）相对提升达阈值（固化：≥3% 相对提升），且 Recall@K 不低于确定性基线；此为 Agent 编排进入默认检索路径的可验证闸口，未达阈值则作为可选检索路径保留、不进入默认路径。
- **SC-002**: 在 001 Markdown/Java 11 条基线（`baseline_report.json`）上交叉验证 Agent 编排路径的 Recall@K/MRR/nDCG 非劣于 001 确定性基线（非劣判定容差按 research.md 声明：Recall@K 精确、MRR/nDCG 1% 相对容差），确认 Agent 编排未对 001 已验证格式造成回归（蓝图 §23.4.5、§24.3）。
- **SC-003**: 验收测试集中 Agent 编排检索的跨项目泄漏事件数为零（证据账本、缺口判断、补充检索轮次与上下文编排均受 `project_scope`/`knowledge_scope_id`/`project_id`/`index_version` 约束，跨项目证据不产生返回）。
- **SC-004**: 验收测试集中所有 Agent 编排检索 Tool 成功响应 100% 通过 `search_knowledge` 与 `get_evidence` 输出 Schema 校验（005 不修改对外契约）。
- **SC-005**: 验收测试集中所有 Agent 编排返回的证据 100% 可定位到确定的知识源版本与内容位置（沿用 001/003 来源定位格式）。
- **SC-006**: 验收测试集中每条返回证据可在追加式证据账本中解析到其检索查询、检索器、得分、版本、来源与产生轮次；且账本原始记录未被任何 Agent 改写（蓝图 §13、宪法原则 IV）。
- **SC-007**: Agent 编排单次调用的 P50/P95 延迟与模型成本被记录，并与同一环境会话内重跑的确定性基线对照（保证延迟增量公平，FR-030）；延迟允许因多 Agent 与补充检索上升，但 MUST 不超过服务端总超时护栏且小于目标 MCP Host 的 Tool Call 超时（蓝图 §19）。
- **SC-008**: 对照评测可重复：同一环境连续两次运行的 Recall@K、MRR、nDCG 在容差内一致（沿用 001/002/004 非延迟可重复性要求）；延迟与成本指标标注为环境敏感。
- **SC-009**: 对照评测报告逐查询展示确定性基线排名与 Agent 编排排名差异，且对每个排名变化提供各 Agent 判断（拆解子问题、信号选择、缺口/冲突判断、补充检索轮次、上下文编排决策）与证据账本引用以解释变化（宪法原则 IV）。
- **SC-010**: 证据分析 Agent 在复杂场景中区分硬证据与推断证据；推断证据不静默覆盖冲突的硬证据；冲突与缺口显式返回而非臆造裁决（蓝图 §11.2、§14、宪法原则 III）。
- **SC-011**: 当某 Agent 结构化输出未通过 Schema 校验、节点超时或 Agent 编排被关闭时，系统回退到该角色/路径的确定性等价行为并仍返回有效 `completion_status` 四态结果（`complete`/`partial`/`no_evidence`/`failed`），不因 Agent 失败而无法响应（蓝图 §14、§15、§19）。
- **SC-012**: DeepSeek Harness 为本机已安装的必过参考客户端（Agent 编排 `search_knowledge` 与 `get_evidence` 端到端调用与输出 Schema 校验必须通过），ChatGPT App 与 Claude Code 记录兼容性状态、不作 005 验收阻塞项；Agent 路径 30s 总超时护栏须低于三端最低 Tool Call 超时，超时则降级 `partial`（沿用 001 SC-005、蓝图 §19）。
- **SC-013**: 同一后端在 5 个并发请求的验收场景中不发生 LangGraph 状态、证据账本或项目作用域串扰（沿用 001 SC-008 并发隔离，蓝图 §21）。
- **SC-014**: Agent 推理结果不自动写回项目知识库；运行状态使用 TTL；追踪配置可关闭查询正文与证据正文记录（蓝图 §20）。
- **SC-015**: 002/004 确定性增强路径原有非 Agent 受益查询在 Agent 编排下 MRR/nDCG 非劣（沿用 1% 相对容差，值在 research.md）、Recall@K 不下降，作为进入默认检索路径的非回归闸口之一，与 SC-001 受益子集提升、SC-002 001 非劣共同构成完整三段通过判定（宪法原则 X，对齐 004 SC-013 模式）。
