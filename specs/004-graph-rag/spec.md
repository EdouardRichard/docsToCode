# Feature Specification: Graph RAG

**Feature Branch**: `004-graph-rag`

**Created**: 2026-08-28

**Status**: Draft

**Input**: User description: "PostgreSQL 图关系 + 硬关系 + 软关系 + 1~3 跳扩展。范围依据：蓝图 §23.4.4 / §10 / §8.2。输入材料：混合检索代码、Java 调用图 / DDL 外键语料。"

**Scope Basis**: 蓝图 §23.4.4（004 纵向交付 Feature 定义：PostgreSQL 图关系、硬关系、软关系与有限跳扩展，并与混合检索基线对照）、§10（双层图谱：硬关系 §10.1 / 软关系 §10.2）、§8.2（PostgreSQL 拥有图节点、图边、硬关系与软关系；Graph RAG 首期使用 PostgreSQL 关系表与递归查询完成一至三跳关系扩展）、§8.3（不引入 Neo4j；通过 Graph Store 抽象保留迁移能力）、§9（PostgreSQL 图关系扩展是混合检索链路的第 3 信号）、§5（知识版本能力清单新增 `graph_ready`）、§24（评测驱动：增强须证明收益且不违反硬性指标后才进入默认检索路径）。

## 对照对象（基线）

本 Feature 的对照评测对象同时声明两档基线，以满足宪法原则 X（评测驱动优化）与蓝图 §24.3（后续 Feature 必须在 research.md 声明相对基线目标）：

### 基线 A — 001 确定性 Dense 基线（Markdown / Java 基线）

Feature `001-minimum-rag-mcp-loop` 建立的确定性 Dense-only 基线，数据记录于 `eval/baseline_report.json`。这是"无任何增强"的确定性基线，也是本 Feature 首期硬关系语料（Java 调用图）的来源格式基线：

| 指标 | 001 Dense 基线值 |
|------|-----------------|
| 评测集查询数 | 11（Markdown + Java） |
| Recall@K（mean, K=5） | 1.0 |
| MRR（mean） | 0.9091 |
| nDCG@K（mean） | 0.9329 |
| 延迟 P50 | 138.45 ms |
| 延迟 P95 | 185.15 ms |
| 嵌入模型 | BAAI/bge-m3 |
| Qdrant 集合 | `chunks_dense_bge-m3_v1`（Dense-only） |

**关键弱点用例**：查询 5（`Find the definition of com.example.service.UserService#validateToken.`）期望证据（方法级 Chunk）在 Dense 基线中排名第 2，类级 Chunk（0.6151）略高于方法级 Chunk（0.6133），语义相似度无法稳定区分精确符号及其调用上下文。图关系扩展的价值正是为这类"语义/词汇相近但结构性不同"的证据补充确定性调用链与外键结构上下文，使方法级及其调用者/被调用者证据获得可解释的结构权重。

### 基线 B — 002 混合检索基线（Dense + Sparse + 融合 + Rerank）

Feature `002-hybrid-retrieval-precision` 建立的混合检索基线，数据记录于 `eval/hybrid_comparison_report.json`。图关系扩展作为蓝图 §9 检索链路的第 3 信号叠加在混合检索之上，因此必须与混合基线对照：

| 指标 | 002 混合基线值 |
|------|----------------|
| 评测集查询数 | 18（Markdown + Java，含中文与词汇精确查询） |
| Recall@K（mean） | 1.0 |
| MRR（mean） | 0.9722 |
| nDCG@K（mean） | 0.9795 |
| 延迟 P50 | 152.40 ms |
| 延迟 P95 | 189.34 ms |
| 融合算法 | RRF |
| Reranker | `BAAI/bge-reranker-v2-m3` |
| 硬性指标 | 跨项目泄漏 = 0 / Schema 合法率 100% / 来源可定位率 100%，均已通过 |

**对照说明**：002 在其 18 条评测集上相对 Dense 基线的 MRR/nDCG 增量为 0（逐查询排名均未变化，含 validateToken 用例仍排第 2），证明词汇与语义融合无法独立解决结构性关系召回。图增强须在"结构性受益查询"子集上证明相对混合基线的可度量收益（见 FR-019 与 SC-001），并同时在 001 Markdown/Java 11 条基线上交叉验证不引入回归（FR-018）。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Java 调用图硬关系召回与可验证证据 (Priority: P1)

外部 Agent（ChatGPT App、DeepSeek Harness、Claude Code）查询一个方法、类或调用链时，系统从已发布的 Java 知识源中由确定性解析产生的调用图硬关系（类/函数调用、方法调用、API 实现与调用）出发，执行 1 至 3 跳关系扩展，把语义/词汇召回遗漏的调用者、被调用者与相邻符号作为**硬关系证据**补充进检索结果，并明确标记为可验证证据。

**Why this priority**: Java 调用图是本 Feature 首期硬关系语料之一（蓝图 §10.1：类或函数调用、API 实现与调用；蓝图 §9：模块、接口、表和调用关系由图关系补充）。001 Dense 与 002 混合基线已暴露"语义/词汇相近但结构性不同"证据难以区分（validateToken 方法级证据排第 2）。调用图扩展直接服务 Agent 一次拿到正确调用上下文的能力，是 004 相对 001/002 的核心增量。

**Independent Test**: 对一个已发布且声明 `graph_ready` 的 Java 知识版本，在固定评测集的"调用链受益"查询子集上运行图增强检索，验证调用者/被调用者证据被召回且标记为硬关系证据，MRR/nDCG 相对混合基线有可度量提升，且不引入跨项目证据。

**Acceptance Scenarios**:

1. **Given** 一个已发布且声明 `graph_ready` 的 Java 知识版本，**When** Agent 携带显式项目作用域查询某方法的调用上下文，**Then** 系统基于调用图硬关系执行 1~3 跳扩展，召回该方法的调用者与被调用者证据，每条硬关系证据标记为可验证证据并携带来源 ID、版本与位置。
2. **Given** 查询方法级符号在混合基线中因类级证据语义相近而排名靠后（如 validateToken 用例），**When** 图增强将调用链相关证据按结构权重并入候选，**Then** 方法级及其调用上下文证据在融合后排名不劣于混合基线，且排名变化可由图关系扩展路径解释。
3. **Given** 某调用关系只存在于作用域外的项目，**When** Agent 仅携带本项目作用域查询，**Then** 系统不返回作用域外的图扩展证据，跨项目泄漏事件数为零。

### User Story 2 - DDL 外键硬关系召回与可验证证据 (Priority: P1)

外部 Agent 查询一张表、字段或其引用关系时，系统从已发布的 DDL 知识源中由确定性解析产生的外键硬关系（表、字段与外键；蓝图 §10.1）出发，执行 1 至 3 跳扩展，把语义/词汇召回遗漏的被引用表、引用方表与级联字段作为**硬关系证据**补充进检索结果，并标记为可验证证据。

**Why this priority**: DDL 外键是本 Feature 首期硬关系语料之一（蓝图 §10.1：表、字段和外键）。表与字段的引用关系由图关系补充（蓝图 §9），是 Agent 理解数据模型与跨表依赖的确定性来源。

**Independent Test**: 对一个已发布且声明 `graph_ready` 的 DDL 知识版本，在固定评测集的"外键受益"查询子集上运行图增强检索，验证被引用表/引用方表证据被召回且标记为硬关系证据，且不引入跨项目证据。

**Acceptance Scenarios**:

1. **Given** 一个已发布且声明 `graph_ready` 的 DDL 知识版本，**When** Agent 携带显式项目作用域查询某表被哪些表外键引用，**Then** 系统基于外键硬关系执行 1~3 跳扩展，召回引用方表与级联字段的证据，每条硬关系证据标记为可验证证据并携带来源 ID、版本与位置。
2. **Given** 查询某字段的外键目标表在混合基线中未被召回，**When** 图增强沿外键边扩展，**Then** 目标表证据被并入候选并携带外键关系路径，使证据召回的结构覆盖度相对混合基线有可度量提升。
3. **Given** 某外键关系连接的两张表分属不同项目知识域，**When** Agent 仅携带单项目作用域查询，**Then** 系统只在作用域内沿外键边扩展，跨项目的图边不产生返回证据，跨项目泄漏事件数为零。

### User Story 3 - 图增强检索在结构性受益查询上优于混合基线 (Priority: P1)

系统将 PostgreSQL 图关系扩展候选作为混合检索链路的第 3 路输入并入 RRF/DBSF 融合池（与 Dense/Sparse 候选同池），融合后统一 Cross-Encoder Rerank，使"调用链 / 外键链路等结构性受益"查询的 MRR 与 nDCG 相对 002 混合基线有可度量提升，同时 Recall@K 不下降、硬性验收指标不被违反，且相对 001 Markdown/Java 确定性基线不引入回归。

**Why this priority**: 蓝图 §24.3 与宪法原则 X 要求增强必须在固定评测集上证明收益且不违反硬性指标后才进入默认检索路径。002 混合基线在其 18 条集上相对 Dense 的 MRR/nDCG 增量为 0，证明非结构信号已触及天花板；图扩展是下一个须经评测证明的增量。

**Independent Test**: 在固定评测集上运行图增强检索，产出图增强报告并与 `eval/hybrid_comparison_report.json` 对照，验证结构性受益查询子集的 MRR/nDCG 均值有可度量提升、Recall@K 不低于混合基线，并同时在 001 Markdown/Java 11 条基线（`eval/baseline_report.json`）上交叉验证无回归；跨项目泄漏为零、Schema 合法率与来源可定位率均为 100%。

**Acceptance Scenarios**:

1. **Given** 002 混合基线报告与 001 Dense 基线报告，**When** 系统在固定评测集上运行"图增强 = 混合检索 + 图关系扩展"路径，**Then** 结构性受益查询子集的 MRR 与 nDCG 均值相对混合基线有可度量提升，Recall@K 不低于混合基线。
2. **Given** 图增强路径含 Dense/Sparse/融合/Rerank/图扩展多个子步骤，**When** 图扩展子步骤失败或超时而混合检索已有可靠证据，**Then** 系统返回 `partial` 状态并携带已验证证据与失败路径信息，不返回空结果或伪造证据（沿用 001/002 四态）。
3. **Given** 001 Markdown/Java 11 条基线查询，**When** 在同一环境会话内重跑图增强路径，**Then** 这 11 条的 Recall@K/MRR/nDCG 不劣于 001 Dense 基线（非劣判定容差按 research.md 声明：Recall@K 精确、MRR/nDCG 1% 相对容差），确认图扩展未对已有格式造成回归。

### User Story 4 - 软关系推断且不伪装为项目事实 (Priority: P2)

系统通过 LLM 从文档与代码中推断业务概念与隐含关系（软关系），每条软关系必须保存推断来源、置信度、模型与版本、生成时间与支撑证据 ID；MCP 返回结果必须明确区分硬关系（可验证证据）与推断关系，软关系不得伪装为项目事实。

**Why this priority**: 蓝图 §10.2 与宪法原则 III（暴露不确定性）要求推断图关系必须与确定性关系可区分、不得伪造解析。软关系是 004 的第二层图谱，其价值在于补全硬关系无法表达的隐含业务关联，但价值成立的前提是可溯源、可区分、可降权。

**Independent Test**: 对一个已发布的知识版本运行软关系推断，验证每条软关系携带五项必填元数据，验证 MCP 结果中软关系证据与硬关系证据可区分标注，且软关系不得作为唯一依据覆盖冲突的硬关系证据。

**Acceptance Scenarios**:

1. **Given** 已发布知识版本的文档与代码 Chunk，**When** LLM 推断出一条业务概念软关系，**Then** 系统保存推断来源、置信度、模型与版本、生成时间与支撑证据 ID，且该软关系可被独立检索与定位。
2. **Given** 一条软关系与一条硬关系对同一结论产生冲突，**When** 系统组织返回证据，**Then** 两者并列返回并明确区分"硬关系（可验证）"与"推断关系"，软关系不得静默覆盖或冒充硬关系项目事实。
3. **Given** LLM 推断的软关系缺乏可信支撑证据，**When** 系统评估其置信度，**Then** 低置信度软关系不进入默认检索路径或仅作为低权重补充，不得以软关系填补硬证据缺口（宪法原则 III/VI）。

### User Story 5 - 知识版本声明 graph_ready 且图关系可重建与隔离 (Priority: P2)

系统为知识版本发布声明 `graph_ready` 能力；声明该能力的版本必须等待对应图关系就绪后才可变为可检索状态；图节点、图边、硬关系与软关系全部以 `knowledge_scope_id`、`project_id` 与 `index_version` 隔离存储于 PostgreSQL；所有图派生数据可从原始知识源与版本信息重建；图扩展只调用当前已发布版本明确声明的能力。

**Why this priority**: 蓝图 §5（能力清单 `graph_ready`）、§8.2（PostgreSQL 拥有图节点/图边/硬关系/软关系）、§8.4（派生数据可重建）与宪法原则 VIII（知识版本不可混用）是硬约束。图关系是知识版本的派生能力，必须像 Dense/Sparse 一样通过能力清单显式声明与版本隔离。

**Independent Test**: 发布一个声明 `graph_ready` 的知识版本，验证其图关系就绪后才可检索、图数据按项目作用域隔离、删除/清空后图关系不再参与新检索，且可从原始知识源重建全部图派生数据。

**Acceptance Scenarios**:

1. **Given** 一个已发布混合能力（`dense_ready` + `lexical_ready`）的版本，**When** 用户为同一知识源构建并发布图关系，**Then** 新版本能力清单声明 `graph_ready`，发布前图关系（硬关系与软关系）均已就绪，未就绪版本不变为可检索。
2. **Given** 两个独立项目的知识版本各自声明 `graph_ready`，**When** 查询规划选择图扩展信号，**Then** 图扩展只在请求作用域内已发布且声明 `graph_ready` 的版本上执行，跨项目的图边不产生返回证据。
3. **Given** 一个已发布 `graph_ready` 版本，**When** 用户删除该知识源或清空知识域，**Then** 图关系先停止参与新检索，再完成图派生数据删除，且其他项目的图关系不受影响（沿用 001 删除/清空策略，蓝图 §5：清空先标记不可检索再异步删除图关系）。
4. **Given** 一个声明 `graph_ready` 的版本，**When** 用户从原始知识源与版本信息重建，**Then** 系统能够重建全部图派生数据（硬关系与软关系），沿用蓝图 §8.4 与 001/002/003 重建能力。

### Edge Cases

- 当 Java 源文件因语法错误无法形成完整 AST、无法确定性提取调用边时，系统必须报告硬关系提取降级或失败并说明原因，不得伪造调用关系（沿用 001 Java AST 降级策略，宪法原则 III）。
- 当 DDL 文件不含外键约束、或外键引用对象不在本项目知识域时，系统必须只对可确定的外键关系产生硬边，不得跨项目补全或推断外键。
- 当图扩展在 1~3 跳内产生大量候选（如高扇出调用方法）时，系统必须按护栏截断，保留结构权重最高的可定位证据，不因扇出爆炸而突破延迟或证据预算（蓝图 §12 护栏）。
- 当图扩展子步骤超时而混合检索已有可靠证据时，系统必须返回 `partial` 并标注超时路径，不阻塞返回（沿用 002 降级策略）。
- 当一条关系同时存在硬关系与软关系判定（如既可由 AST 确定又可由 LLM 推断）时，系统必须以硬关系为准，软关系不得覆盖硬关系的可验证判定（宪法原则 III：推断关系与确定性关系可区分）。
- 当 LLM 推断的软关系置信度低于阈值或缺乏支撑证据 ID 时，系统必须将其排除出默认检索路径或降为低权重补充，不得以推断填补硬证据缺口。
- 当一个知识版本声明 `graph_ready` 但底层图关系因数据损坏不可用时，系统必须将该版本视为不可检索或降级为混合检索，不得静默返回残缺图扩展结果。
- 当同一查询跨多个并发请求调用图增强检索时，请求级作用域、证据账本与图扩展中间状态不得互相污染（沿用 001/002/003 并发隔离）。
- 当对照评测重复运行时，非延迟指标必须在容差内一致；延迟指标因环境波动允许超出容差但必须记录并标注（沿用 001/002/003 可重复性边界）。
- 当图扩展召回的证据其来源版本已被撤销时，系统不得以其他版本内容静默替代该图证据（沿用 001 FR-020）。

## Requirements *(mandatory)*

### Functional Requirements

**双层图谱构建（蓝图 §10）**

- **FR-001**: 系统 MUST 在入库流程中，为声明 `graph_ready` 的知识版本从已切片的 Java Chunk 与 DDL Chunk 出发，由确定性解析提取**硬关系**并写入 PostgreSQL 图节点与图边（蓝图 §5 步骤 4 建立图关系；§8.2 PostgreSQL 拥有图节点/图边/硬关系/软关系）。硬关系 MUST 覆盖本 Feature 首期语料：Java 调用图（类/函数调用、方法调用、API 实现与调用）与 DDL 外键（表、字段与外键）（蓝图 §10.1）。
- **FR-002**: 硬关系 MUST 标记为可验证证据。每条图边 MUST 携带规范标识字段：`edge_id`、`source_chunk_id`（调用方/外键引用方）、`target_chunk_id`（被调用方/被引用方）、`relation_type`(枚举 `{calls, called_by, fk_references, fk_referenced_by, other_hard}`)、`direction`(out|in)、`is_hard`=true、`version`，并带 `knowledge_scope_id`/`project_id`/`index_version` 隔离字段与确定性解析依据，使关系可被独立定位与审计（蓝图 §10.1：硬关系标记为可验证证据；宪法原则 IV：来源可定位）。
- **FR-003**: 系统 MUST 允许通过 LLM 从文档与代码中推断**软关系**（业务概念与隐含关系）并写入 PostgreSQL；每条软关系 MUST 保存推断来源、置信度、模型与版本、生成时间与支撑证据 ID 五项元数据（蓝图 §10.2），并 MUST 携带四态生命周期状态 `inferred`/`active`/`superseded`/`retired`：推断产出为 `inferred`，置信度 ≥ 阈值且经支撑证据校验后为 `active`（进入默认检索路径作低权重补充），被同源硬关系取代或被新软关系覆盖为 `superseded`（保留可追溯但不参与检索）；该转换 MUST 由确定性规则触发、不得由 LLM 独占判定（宪法原则 VI）：同 `(source_chunk_id, target_chunk_id, relation_type)` 三元组的新推断置信度高于现存 `active` 软关系时，旧者转 `superseded`、新者转 `active`；同对出现硬关系时相关 `active` 软关系直接转 `superseded`（硬关系为准，宪法原则 III），版本撤销/清空删除为 `retired`；软关系 MUST NOT 升级为硬关系，硬关系只能由确定性解析产生（宪法原则 III）。
- **FR-004**: 软关系 MUST NOT 伪装为项目事实：MCP 返回结果 MUST 明确区分硬关系（可验证证据）与推断关系；当软关系与硬关系冲突时，两者 MUST 并列返回且软关系不得静默覆盖硬关系（蓝图 §10.2、宪法原则 III）。
- **FR-005**: 软关系 MUST 按置信度与支撑证据参与检索：低置信度或缺乏支撑证据 ID 的软关系 MUST NOT 进入默认检索路径，或仅作为低权重补充，MUST NOT 以推断关系填补硬证据缺口（宪法原则 III/VI）。

**一至三跳关系扩展（蓝图 §8.2 / §9）**

- **FR-006**: 系统 MUST 在 PostgreSQL 中使用关系表与递归查询完成常见的一至三跳关系扩展，作为混合检索链路的第 3 路输入并入 RRF/DBSF 融合池（与 Dense/Sparse 候选同池），融合后统一 Cross-Encoder Rerank（蓝图 §8.2：Graph RAG 首期使用 PostgreSQL 关系表与递归查询完成一至三跳；§9：图关系扩展是第 3 信号，位于融合与 Rerank 之前）。
- **FR-007**: 图扩展 MUST 接收由查询规划确定的关系方向与跳数上限（蓝图 §11.1 查询规划选择关系方向），并在 1~3 跳护栏内执行；超过护栏的扇出 MUST 按结构权重截断，保留最高相关的可定位证据（蓝图 §12 护栏）。在 004 阶段（蓝图 §11.1 查询规划 Agent 属 Feature 005、不在本 Feature 内），关系方向 MUST 由确定性配置决定、不得由 LLM 独占（宪法原则 VI）：默认双向遍历成对方向关系类型（`calls`+`called_by`、`fk_references`+`fk_referenced_by`），运行配置可收敛方向子集，评测期固定此默认以保证 SC-007 可重复性。
- **FR-008**: 图扩展 MUST 为每条召回证据保留其图关系扩展路径（从起点 Chunk 经若干硬/软关系边到达该证据的跳序列、关系类型与方向），使"为什么召回这条证据"可解释（宪法原则 IV）。

**作用域与硬约束继承**

- **FR-009**: 图增强检索 MUST 继承 001/002/003 的显式项目作用域要求：缺少显式 `project_scope` 的项目检索 MUST 被拒绝，不得回退默认全库搜索（宪法硬约束）。
- **FR-010**: 图节点、图边、硬关系与软关系 MUST 全部以 `knowledge_scope_id`、`project_id` 与 `index_version` 隔离存储；图扩展 MUST 只在请求作用域内沿边扩展，跨项目泄漏事件数在验收测试集中 MUST 为零（蓝图 §8.2/§8.4、宪法硬约束）。
- **FR-011**: 图增强检索的 Tool 响应 MUST 100% 通过 `search_knowledge` 与 `get_evidence` 输出 Schema 校验（宪法硬约束）；004 不修改 001 已确立的 MCP 对外契约，图扩展证据通过既有契约返回并增补可区分的硬/软关系标注（宪法原则 VII：接口独立演进）。
- **FR-012**: 图增强检索返回的每条证据（含图扩展召回的硬关系证据与软关系证据）MUST 携带来源 ID、版本与可定位位置（Markdown 章节路径、Java 全限定符号路径、DDL 表名/字段名/约束名等，沿用 001/003 来源定位格式），来源可定位率在验收测试集中 MUST 为 100%（宪法硬约束）。

**版本、能力声明与重建**

- **FR-013**: 系统 MUST 允许知识版本发布声明 `graph_ready` 能力；声明 `graph_ready` 的版本 MUST 在对应图关系（硬关系，并在声明软关系时含软关系）就绪后才可变为可检索状态（蓝图 §5：声明 Graph 能力的版本必须等待对应图关系就绪）。
- **FR-014**: 查询规划 MUST 只调用当前已发布版本明确声明的能力；仅声明 `dense_ready`/`lexical_ready` 而未声明 `graph_ready` 的版本 MUST NOT 参与图扩展路径，但 MUST 继续支持 Dense/混合检索（蓝图 §5：查询规划只能调用已发布版本明确声明的能力）。
- **FR-015**: 系统 MUST NOT 将不同嵌入模型或不兼容切片策略产生的图关系混入同一索引版本；图关系作为同一嵌入模型与切片策略上的派生能力扩展，不触发宪法原则 VIII 的"不可混用"（沿用 002 能力扩展论证）。
- **FR-016**: 系统 MUST 能够从原始知识源与版本信息重建全部图派生数据（硬关系与软关系），沿用蓝图 §8.4 与 001/002/003 重建能力；清空操作 MUST 先将知识库标记为不可检索，再异步删除图关系（蓝图 §5）。

**降级、护栏与并发**

- **FR-017**: 系统 MUST 为图增强检索配置护栏：图扩展跳数默认 2、上限 3；图扩展候选预算（单次图扩展整体召回候选总数，按结构权重全局排序截断后并入融合，非逐跳预算）默认 10、上限 20；图扩展查询子超时默认 3s；单次调用总超时沿用 001/002/003 的 30s 且 MUST 小于目标 MCP Host 的 Tool Call 超时（蓝图 §12/§19）。跳数、候选预算与子超时可由运行配置覆盖，但 MUST NOT 超过上述上限。
- **FR-018**: 系统沿用 001 蓝图 §14 四态完成状态（`complete`/`partial`/`no_evidence`/`failed`）：当图扩展子步骤失败或超时、但混合检索已有可靠证据时，系统 MUST 返回 `partial` 状态并携带已验证证据与失败路径信息；当混合检索与图扩展均无可靠证据但非系统异常时返回 `no_evidence`；当系统异常无法形成可靠证据时返回 `failed`（蓝图 §14，沿用 001/002 四态）。
- **FR-019**: 系统 MUST 在图扩展打分或融合打平时保留稳定、确定的次序，不在图扩展或融合中引入随机扰动（宪法原则 VI：确定性控制优先）。
- **FR-020**: 系统 MUST 在同一后端隔离不同 Agent、不同会话与并发请求的运行状态、证据账本与图扩展中间状态，并发场景下不发生串扰（沿用 001/002/003 并发隔离，5 并发，蓝图 §21.1）。
- **FR-028**: 目标 Host 兼容性沿用 001 参考客户端策略：DeepSeek Harness 为本机已安装的必过参考客户端，其端到端调用与输出 Schema 校验 MUST 通过；ChatGPT App 与 Claude Code 记录兼容性状态、MUST NOT 作为 004 验收阻塞项（沿用 001 SC-005）。图增强单次调用总超时 30s 护栏 MUST 低于三者中最低 Tool Call 超时预算（蓝图 §19）。

**对照评测（蓝图 §24 / 宪法原则 X）**

- **FR-021**: 系统 MUST 在 001/002/003 既有固定评测集（`eval/eval_dataset.json`）基础上，新增"结构性受益"图扩展查询（Java 调用链查询如"validateToken 的调用者/被调用者"、DDL 外键链路查询如"引用 users 表的表"、以及中文等价查询），新增 ≥ 6 条且含 ≥ 1 条中文查询，仍遵循 001 的 AI 生成、人工审核、JSON 格式约定；原既有查询保留以保证与基线逐条可比。
- **FR-022**: 系统 MUST 在扩充后的评测集上运行图增强检索评测，产出 Recall@K、MRR、nDCG、P50/P95 延迟指标，并与两档基线对照：相对 002 混合基线（`eval/hybrid_comparison_report.json`）验证结构性受益子集 MRR/nDCG 有可度量提升、Recall@K 不下降；相对 001 Dense Markdown/Java 基线（`eval/baseline_report.json`）验证 11 条原有查询无回归（蓝图 §24.1/§24.3）。
- **FR-023**: 对照评测 MUST 逐查询记录混合基线排名与图增强排名、Dense/Sparse/融合/Rerank 分数与图扩展路径分数（关系类型、跳数、结构权重），使排名变化可解释（宪法原则 IV）。
- **FR-024**: 图增强 MUST 在固定评测集上证明相对 002 混合基线的可度量收益——结构性受益子集 MRR/nDCG 相对混合基线相对提升 ≥ 3%，且 002 原有非结构性查询 MRR/nDCG 非劣（沿用 1% 相对容差，值在 research.md）、Recall@K 不下降，且未违反任何硬性验收指标（跨项目泄漏为零、Schema 合法率 100%、来源可定位率 100%）后，才进入默认检索路径；未达阈值则图扩展作为可选检索路径保留、不进入默认路径（宪法原则 X、蓝图 §24.3）。
- **FR-025**: 对照评测 MUST 在同一环境会话内先重跑混合基线、再运行图增强路径，以保证延迟增量对照公平（沿用 002 延迟对照公平策略）；非延迟指标同时与 `eval/hybrid_comparison_report.json` 及 `eval/baseline_report.json` 交叉验证。
- **FR-026**: 系统 MUST 记录每次图增强检索的请求标识、知识作用域、完成状态、各子路径（Dense/Sparse/融合/Rerank/图扩展）耗时与证据引用（含图关系扩展路径），以支持问题回溯（蓝图 §13 证据账本，沿用 001/002/003 追踪）。
- **FR-027**: 已有混合能力知识版本获得图能力 MUST 通过用户对已有知识源触发重建、发布声明 `graph_ready` 的新版本实现；系统 MUST NOT 自动批量迁移已发布版本，也 MUST NOT 使已发布混合版本在重建期间不可检索（沿用 001/002 失败保护与重建能力）。

### Key Entities *(include if feature involves data)*

- **图节点（Graph Node）**: 以已切片 Chunk 为节点的图顶点（Java 符号 Chunk、DDL 表/字段/约束 Chunk 等），携带 `knowledge_scope_id`、`project_id`、`index_version` 与来源 Chunk ID，沿用 001/003 的 Chunk 标识。
- **图边（Graph Edge）**: 图节点间的关系边，分硬关系（确定性解析产生，`is_hard`=true）与软关系（LLM 推断产生，`is_hard`=false，`relation_type`=`inferred`），携带规范标识字段 `edge_id`/`source_chunk_id`/`target_chunk_id`/`relation_type`(枚举 `{calls, called_by, fk_references, fk_referenced_by, other_hard, inferred}`)/`direction`(out|in)/`version` 与 `knowledge_scope_id`/`project_id`/`index_version` 隔离字段；软关系额外带五项元数据与四态状态。
- **硬关系（Hard Relation）**: 确定性解析产生的关系（Java 调用图、DDL 外键，以及蓝图 §10.1 列举的模块依赖、API 实现与调用、配置引用、测试覆盖等），标记为可验证证据，携带确定性解析依据。
- **软关系（Soft Relation）**: LLM 从文档与代码推断的业务概念与隐含关系，必带推断来源、置信度、模型与版本、生成时间、支撑证据 ID 五项元数据，并携带四态生命周期状态（`inferred`/`active`/`superseded`/`retired`）；与硬关系可区分、不得伪装为项目事实，且不得升级为硬关系。
- **图关系扩展路径（Graph Expansion Path）**: 从起点 Chunk 经若干关系边到达某证据的跳序列（关系类型、方向、跳数），用于解释图扩展召回证据的原因。
- **知识版本能力清单（Capabilities）**: 001/002 已有 `dense_ready`/`lexical_ready`；004 扩展为新增 `graph_ready`，声明 `graph_ready` 的版本才启用图扩展路径。
- **对照评测报告（Comparison Report）**: 在扩充后的固定评测集上记录图增强指标、与 002 混合基线及 001 Dense 基线的逐项增量、逐查询图扩展路径与排名变化的评测产物。

## Success Criteria *(mandatory)*

- **SC-001**: 在固定评测集的"结构性受益"查询子集上，图增强检索（混合检索 + 图关系扩展）的 MRR 与 nDCG 均值相对 002 混合基线（`eval/hybrid_comparison_report.json`）相对提升 ≥ 3%，且 Recall@K 不低于混合基线（不要求提升，要求不下降）；此为图扩展进入默认检索路径的可验证闸口，未达阈值则图扩展作为可选检索路径保留、不进入默认路径。

- **SC-003**: 验收测试集中图增强检索的跨项目泄漏事件数为零（图节点、图边、硬关系与软关系均按 `knowledge_scope_id`/`project_id`/`index_version` 隔离，跨项目图边不产生返回证据）。

- **SC-005**: 验收测试集中所有图增强检索返回的证据（含图扩展召回的硬关系证据与软关系证据）100% 可定位到确定的知识源版本与内容位置（沿用 001/003 来源定位格式）。
- **SC-006**: 图增强检索单次调用的 P50/P95 延迟被记录，并与同一环境会话内重跑的混合基线对照（保证延迟增量公平，FR-025）；延迟允许因新增图扩展步骤而上升，但 MUST 不超过服务端总超时护栏且小于目标 MCP Host 的 Tool Call 超时。
- **SC-007**: 对照评测可重复：同一环境连续两次运行的 Recall@K、MRR、nDCG 在容差内一致（沿用 001/002/003 非延迟可重复性要求）；延迟指标标注为环境敏感。
- **SC-008**: 对照评测报告逐查询展示 002 混合基线排名与图增强排名差异，且对每个排名变化提供 Dense/Sparse/融合/Rerank 分数与图扩展路径分数（关系类型、跳数、结构权重）以解释变化。
- **SC-009**: 硬关系证据与软关系证据在 MCP 结果中可区分标注；软关系携带推断来源、置信度、模型与版本、生成时间与支撑证据 ID 五项元数据；软关系不静默覆盖冲突的硬关系证据（蓝图 §10.2、宪法原则 III）。
- **SC-010**: 知识版本能力清单正确声明 `graph_ready`；未声明 `graph_ready` 的版本不被纳入图扩展路径；声明 `graph_ready` 的版本在图关系就绪后才可检索；图派生数据可从原始知识源与版本信息重建（蓝图 §5/§8.4）。
- **SC-011**: 图扩展子步骤失败或超时时，已有混合检索可靠证据的场景返回 `partial` 并携带失败路径信息；完全无法形成可靠证据时返回 `failed`（四态可区分、可操作，沿用 001/002 SC）。

- **SC-013**: 图增强相对 002 混合基线，其原有非结构性查询（002 评测集原有 18 条中非结构性受益子集部分）MRR/nDCG 非劣（沿用 1% 相对容差，值在 research.md）、Recall@K 不下降，作为进入默认检索路径的非回归闸口之一，与 SC-001 子集提升闸口、SC-002 001 非劣闸口共同构成完整三段通过判定（宪法原则 X）。

- Q: 软关系推断产出后应采用哪组生命周期状态机？ → A: 四态 `inferred`（推断产出）→ `active`（置信度 ≥ 阈值、进入默认检索路径作低权重补充）→ `superseded`（被同源硬关系取代或被新软关系覆盖，保留可追溯但不参与检索）→ `retired`（版本撤销/清空删除）；禁止软关系→硬关系升级，硬关系只能由确定性解析产生。

- Q: 图边/关系类型的规范枚举与图边标识字段应在本规格固化为哪组契约？ → A: 关系类型枚举为 `{calls, called_by, fk_references, fk_referenced_by, other_hard, inferred}`（首期四类覆盖 Java 调用图与 DDL 外键，`other_hard` 保留框架扩展占位，`inferred` 为软关系）；图边标识字段固化为 `edge_id`、`source_chunk_id`、`target_chunk_id`、`relation_type`(枚举)、`direction`(out|in)、`is_hard`(bool)、`version`，并带 `knowledge_scope_id`/`project_id`/`index_version` 隔离字段；软关系额外携带 FR-003 五项元数据与四态状态。
