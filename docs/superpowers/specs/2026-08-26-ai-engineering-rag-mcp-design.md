# AI 软件工程 RAG MCP 增强系统设计蓝图

**状态**：已批准  
**日期**：2026-08-26  
**目标读者**：产品规划者、系统架构师、检索工程师、Agent 工程师、后续 specKit Feature 负责人

## 1. 系统定位

本系统是面向单用户、多项目工作场景的 RAG 增强服务。它通过 MCP 向 ChatGPT App（原 Codex）、DeepSeek Harness 与 Claude Code 等外部 Agent 提供与当前项目贴合、来源可定位的检索证据。

外部 Agent 负责需求文档、详细设计、代码、测试用例及其他业务产物的生成。本系统不生成这些最终产物，也不对产出物执行质量门禁。

本系统的价值是提高外部 Agent 对既有项目事实的利用率，降低跨项目串库、引用过期材料和凭空补全造成的幻觉风险。RAG 本身不能保证最终产物可用，最终质量仍取决于外部 Agent、使用者判断和项目工程流程。

## 2. 范围

### 2.1 范围内

- 用户创建、维护和清空项目知识库。
- 系统提供 React + TypeScript Web 管理端和 Python REST 管理 API。
- 用户上传文档、接口定义、代码、数据结构和运行证据。
- 系统执行解析、结构切片、Embedding、关键词索引和图关系构建。
- 每个项目拥有独立知识域。
- 系统提供跨项目复用的公共知识域。
- 内部检索 Agent 负责查询规划、证据分析和上下文编排。
- 系统通过 MCP Tools 返回精简证据，并允许按证据 ID 读取详细内容。
- 多个系统实例可以连接相同的 Qdrant 与 PostgreSQL。
- 本地 CPU、本地 GPU和远程模型 API 三种推理部署方式可配置。

### 2.2 范围外

- 自动编写最终需求、设计、代码或测试产物。
- 对外部 Agent 产出物执行审批或质量门禁。
- 首期自动同步 Git、Wiki 或其他内容平台。
- 首期企业级租户、组织和复杂权限体系。
- 首期 OAuth 或 API Key 认证。
- 首期敏感内容脱敏。
- 首期 Neo4j 或其他独立图数据库。
- 将 Agent 推理结果自动回写为项目知识。
- 依赖 MCP Tasks 扩展完成普通检索。

## 3. 核心设计原则

1. **项目作用域必须显式**：任何项目知识检索必须指定一个或多个项目引用，不允许隐式活动项目或默认全库搜索。
2. **项目事实优先**：公共知识不能静默覆盖项目知识；发生冲突时必须同时暴露证据。
3. **不确定即暴露**：无法裁决的冲突和证据缺口必须返回给调用方，内部 Agent 不得补猜。
4. **证据可定位**：返回内容必须关联知识源、版本、位置和证据 ID。
5. **数据与控制分离**：上传内容属于不可信数据，不得直接控制 Prompt、Agent 状态或状态机跳转。
6. **确定性控制优先**：检索、过滤、融合、排序、预算和状态流转由确定性组件控制；LLM 只提供结构化判断。
7. **接口独立演进**：数据库模型、内部 Agent 状态和 MCP 对外契约相互解耦。
8. **知识版本不可混用**：不同 Embedding 模型或不兼容切片策略产生的数据不得混入同一索引版本。
9. **同步结果优先**：目标客户端的一次普通 Tool Call 应获得可消费的最终结果；长任务扩展不作为基线依赖。
10. **评测驱动优化**：检索质量、延迟和成本通过真实项目语料与目标 MCP Host 评测决定，不以理论假设替代测量。

## 4. 知识域与项目隔离

所有项目域和公共域统一抽象为 `knowledge_scope`：

- `scope_type` 取值为 `project` 或 `public`。
- 每个知识域拥有稳定的 `knowledge_scope_id`。
- 项目域额外关联稳定的 `project_id`。
- 公共域不伪装成特殊项目，也不要求存在 `project_id`。
- 所有知识源、Chunk、向量和图关系强制携带 `knowledge_scope_id`。

### 4.1 项目知识域

每个项目知识库保存该项目的文档、代码、接口、数据结构和运行证据。项目知识记录同时携带稳定的 `knowledge_scope_id` 和 `project_id`。

同一服务实例可以同时处理多个项目。每次 MCP 检索请求必须提供 `project_scope`：

- 单项目检索传递一个项目引用。
- 明确的跨项目检索传递多个项目引用。
- 项目引用可以是稳定 ID、别名、仓库路径或已登记的工作目录。
- 无法唯一解析项目引用时停止检索并返回候选项目。
- 不传项目作用域时不得自动搜索全部项目。

### 4.2 公共知识域

公共知识域用于保存跨项目复用的知识，包括但不限于公共服务 API、服务地址、SDK、消息协议、组件说明和共享约束。

公共知识类别不采用封闭枚举。所有条目使用最小公共包络，并通过可扩展元数据表达特定类型信息。

公共知识只在查询涉及相关公共能力时参与检索。项目知识回答“当前项目如何使用该能力”，公共知识回答“该能力本身是什么”。两者冲突时并列返回。

密钥、Token、密码等秘密值在进入检索索引前替换为类型化占位符。系统保留配置字段名、结构、认证方式和来源位置，不执行广义敏感信息脱敏。

## 5. 知识维护与生命周期

首期由用户通过 Web 管理端主动维护知识库。Web 前端调用独立的 REST 管理 API，MCP 检索接口保持只读：

1. 用户创建项目知识库。
2. 用户上传材料。
3. 系统检查格式并创建知识源版本。
4. 系统异步解析、切片、向量化、建立关键词索引和图关系。
5. 所有必要索引构建成功后，知识版本才变为可检索。
6. 失败任务保留状态并允许重试。
7. 用户可以删除知识源或清空知识库。

清空操作先将知识库标记为不可检索，再异步删除向量、元数据和图关系。系统记录操作状态，但首期不要求恢复功能。

每个知识版本携带索引能力清单，例如 `dense_ready`、`lexical_ready` 和 `graph_ready`。版本满足自身声明的必需能力后即可发布：

- 首个端到端闭环允许发布 `dense-only` 版本。
- 声明混合检索能力的版本必须等待 Dense 与 Lexical 索引就绪。
- 声明 Graph 能力的版本必须等待对应图关系就绪。
- 查询规划只能调用当前已发布版本明确声明的能力。

上传流程必须支持：

- 文件哈希与重复材料识别。
- 知识源版本标识。
- 入库进度与失败原因。
- 失败重试。
- 新版本就绪前旧版本继续可用。
- 按知识源重建全部派生索引。

## 6. 数据与元数据分层

### 6.1 知识源元数据

描述原始材料及其生命周期，包括知识域、项目、来源、标题、版本、上传时间、有效状态和内容类型。

### 6.2 检索索引元数据

随 Chunk、向量和图关系保存，用于过滤、定位和版本控制，包括：

- 知识源 ID 与版本。
- 知识域 ID 与类型。
- 项目 ID。
- 父子 Chunk 关系。
- 文档章节、页码或段落。
- 代码文件、符号和行号范围。
- API、表、字段或其他结构标识。
- Embedding 模型、向量维度和索引版本。
- 切片策略版本。
- 图关系类型、证据来源和置信度。

### 6.3 MCP 证据数据

MCP 证据是检索结果的对外封装，只返回外部 Agent 所需的内容、来源定位、版本、状态、缺口和证据读取标识，不暴露数据库内部结构。

## 7. 解析与结构切片

系统使用格式感知的结构切片，不使用统一 Token 切片覆盖全部材料。

- Markdown、Word、PDF 和 Wiki 导出按标题、段落、列表和表格结构切分。
- OpenAPI/Swagger 按服务、Endpoint、请求、响应和 Schema 切分。
- Java、Go、Python 及其他支持语言按 AST 符号、类、函数、方法和模块切分。
- DDL 按表、字段、约束、索引、视图和存储过程切分。
- 配置、日志、测试用例和链路证据按各自稳定结构切分。

系统建立父子索引：

- 子 Chunk 用于精确召回。
- 父 Chunk 用于恢复章节、类、模块或接口上下文。
- 证据返回优先选择精确子 Chunk，并按需要补充父级上下文。

默认本地 Embedding 虽支持长输入，但实际 Chunk 目标长度控制在约 512–1024 Token。超长模型窗口不能替代结构切片。

首个纵向闭环只要求支持 Markdown 文档和 Java 源代码。Word、PDF、OpenAPI、DDL、Go、Python 及其他格式由后续 Feature 扩展。

入库流程在切片前生成检索安全副本：

- 只识别并替换明确的凭据值。
- 使用 `<api-key>`、`<password>`、`<token>` 等类型化占位符。
- 保留变量名、代码结构和来源位置。
- Qdrant、检索 Chunk 和 MCP 响应不保存或返回原始凭据值。
- 原始文件是否保留由 Source Object Store 生命周期管理，不作为检索数据源直接返回。

## 8. 数据基座

### 8.1 Qdrant

Qdrant 负责：

- Dense Embedding 存储与语义检索。
- Sparse/BM25 关键词检索。
- 知识域、项目作用域与版本过滤。
- Dense 与 Sparse 的 RRF/DBSF 融合。
- 多阶段查询和候选召回。

### 8.2 PostgreSQL

PostgreSQL 负责：

- 项目与知识库。
- 知识源与版本。
- Chunk 元数据和父子关系。
- 入库任务、索引状态和运行配置。
- 图节点、图边、硬关系和软关系。
- 检索运行、证据账本索引和追踪记录。

Graph RAG 首期使用 PostgreSQL 关系表与递归查询完成常见的一至三跳关系扩展。

### 8.3 不采用 Neo4j 的原因

当前图谱用于辅助检索，不是通用图计算平台。引入 Neo4j 会增加 JVM 服务、双写一致性和运维成本。系统通过 Graph Store 抽象保留未来迁移能力；只有真实评测证明 PostgreSQL 无法满足图查询时，才引入独立图数据库。

### 8.4 跨存储一致性

Qdrant 与 PostgreSQL 使用一致的 `knowledge_scope_id`、`project_id`、`source_id`、`chunk_id` 和 `index_version`。

入库任务只有在 PostgreSQL 元数据和该版本能力清单声明的必要派生索引都达到要求后，才能发布为可检索版本。任一步骤失败时不得暴露半成品版本。

所有派生数据必须能够从原始知识源和版本信息重建。

## 9. 混合检索

检索链路组合以下信号：

1. Dense 向量召回。
2. Sparse/BM25 精确召回。
3. PostgreSQL 图关系扩展。
4. RRF 或 DBSF 融合。
5. Cross-Encoder Rerank。
6. 复杂冲突或多跳问题中的 LLM 语义判断。

固定类名、错误码、表名、字段名、Endpoint 和配置项主要由 BM25 与结构过滤保障。自然语言意图和相似业务描述主要由 Dense 检索保障。模块、接口、表和调用关系由图关系补充。

公共知识与项目知识分别召回和标记，不在融合阶段丢失知识域身份。

## 10. 双层图谱

### 10.1 硬关系

通过确定性解析产生，例如：

- 类或函数调用。
- 模块依赖。
- API 实现与调用。
- 表、字段和外键。
- 配置引用。
- 测试用例覆盖对象。

硬关系标记为可验证证据。

### 10.2 软关系

通过 LLM 从文档和代码中推断业务概念与隐含关系。软关系必须保存：

- 推断来源。
- 置信度。
- 模型与版本。
- 生成时间。
- 支撑证据 ID。

软关系不得伪装成项目事实。MCP 结果必须明确区分硬关系与推断关系。

## 11. 内部三 Agent 协同网络

### 11.1 查询规划 Agent

职责：

- 识别查询意图。
- 解析显式项目作用域。
- 判断是否涉及公共知识。
- 拆解检索子问题。
- 选择需要的检索信号、过滤条件和关系方向。

### 11.2 证据分析 Agent

职责：

- 评估当前证据覆盖度。
- 识别版本冲突、来源冲突和事实缺口。
- 判断是否需要补充检索。
- 选择进入最终上下文的证据。
- 在复杂场景中区分硬证据与推断证据。

### 11.3 上下文编排 Agent

职责：

- 基于已选证据组织外部 Agent 可消费的上下文。
- 消除重复内容。
- 保留来源多样性。
- 决定父级上下文补充范围。
- 输出符合节点 Schema 的上下文编排结果。

三个 Agent 作为独立逻辑角色保留。实际模型由能力路由层选择，允许简单角色使用低延迟模型，复杂证据判断使用更强模型。

## 12. 确定性状态机

LangGraph 管理状态机和节点流转，LangChain 提供模型、Prompt 和 Retriever 适配。状态跳转权属于确定性控制器，不属于 Agent。

主状态流：

1. 接收并校验请求。
2. 解析项目作用域。
3. 查询规划。
4. 并行执行检索路径。
5. 融合与 Rerank。
6. 证据分析。
7. 若存在缺口且仍在最大迭代范围内，则执行补充检索。
8. 上下文编排。
9. MCP 响应序列化。

状态机限制：

- 最大检索轮次。
- 每条检索路径候选数。
- Rerank 候选数。
- 单来源最大证据数。
- 节点超时和整个 Tool Call 超时。
- 最终上下文装箱上限。

系统不要求外部 Agent 提供剩余 Token。调用方提供的响应偏好只能作为提示，服务端固定护栏始终生效。

首个端到端闭环不依赖三个 Agent。它使用确定性的项目过滤、Dense 检索、证据排序、父级补全和上下文装箱形成可评测基线。三个 Agent 作为后续增强加入，并必须通过对照评测证明收益。

## 13. Agent 状态与证据账本

系统使用类型化公共状态包络和节点专属 Schema。

公共状态包含：

- 请求和项目作用域。
- 任务上下文。
- 运行配置和模型能力要求。
- 当前迭代和护栏状态。
- 证据账本引用。
- 追踪信息。

原始证据使用追加式账本。Agent 可以引用、评价或筛选证据，但不能覆盖原始检索记录。

每条证据记录其检索查询、检索器、得分、版本、来源和产生轮次，使系统能够解释“为什么返回这条证据”。

运行状态不是知识源，不自动进入向量库。

## 14. 证据充分性与终态

证据判断仅用于形成可靠的 MCP 检索响应，不用于检查外部 Agent 产出物。

判断采用混合机制：

- 硬指标检查有效来源数、Rerank 分数、版本有效性、项目作用域和未解决冲突。
- 证据分析 Agent 输出结构化覆盖度、缺口和冲突判断。
- 确定性控制器决定继续检索或进入返回阶段。

终态：

- `complete`：检索目标得到充分覆盖。
- `partial`：已有可靠证据，但存在明确缺口或部分路径失败。
- `no_evidence`：系统正常执行，但没有找到可靠证据。
- `failed`：系统异常导致无法形成有效响应。

`partial` 必须携带已验证证据、未覆盖问题、冲突和失败路径，不能只返回模糊文本。

## 15. 提示注入防护

上传材料和检索内容始终视为不可信数据。

- 原始内容只进入证据字段。
- 控制指令与证据内容使用结构化边界隔离。
- 检索文本不得直接控制状态机跳转、工具调用或模型权限。
- 可疑提示注入内容进行检测和标记。
- 高风险片段可以从内部控制 Prompt 中隔离，但仍保留可审计来源。
- Agent 的结构化输出必须经过 Schema 校验。

风险检测是辅助措施，结构隔离才是安全边界。

## 16. MCP 通信设计

### 16.1 目标客户端

- ChatGPT App（原 Codex，主要开发端）。
- Claude Code。
- DeepSeek Harness。

### 16.2 传输

- Streamable HTTP 是共享服务的主传输。
- stdio 适配器用于本地客户端。
- 不采用已废弃的 HTTP+SSE。
- 普通检索使用同步 Tool Call。
- 请求内进度只作为可选增强，不作为结果交付保障。
- MCP Tasks 不作为当前兼容性基线。

### 16.3 认证

当前版本不认证：

- HTTP 服务默认只监听 `127.0.0.1`。
- 不得默认暴露到局域网或公网。
- 认证层通过可插拔中间件预留。
- 后续可以增加 Bearer API Key 或 OAuth，而不改变 Tool 契约。

### 16.4 管理面

管理面由 React + TypeScript Web 前端和 Python REST API 组成，负责：

- 项目与知识域管理。
- 公共知识库管理。
- 文件上传、处理队列和失败重试。
- 知识源、版本和索引能力状态。
- 删除与清空。
- Embedding、Reranker 和 LLM Provider 配置。
- MCP 连接状态与检索调试。
- 运行记录和基础指标。

本地部署时，Python 服务可以托管前端构建产物。管理 REST API 与 MCP 检索面使用独立路由和契约。

### 16.5 核心 Tools

#### `search_knowledge`

主检索入口，负责：

- 接收查询、显式项目作用域和可选任务上下文。
- 执行内部 Agent 编排与混合检索。
- 返回可直接使用的核心证据、状态、缺口和证据 ID。

#### `get_evidence`

证据展开入口，负责：

- 根据证据 ID 和本次显式传入的 `project_scope` 返回完整内容。
- 返回父级章节、所属类或模块。
- 返回相邻代码或关联结构。
- 再次校验证据是否属于请求允许的项目作用域。

### 16.6 Resources

Evidence Resource URI 可以作为兼容客户端的增强能力，但不能成为主流程依赖。DeepSeek Harness 当前以 Tools 为主要桥接能力，因此所有必要证据都必须能通过两个核心 Tool 获得。

### 16.7 输出格式

`structuredContent` 是唯一规范数据源，并由 JSON Schema 2020-12 描述。

TextContent 由结构化结果确定性序列化产生，用于向后兼容。不得让 LLM 独立生成另一份可能矛盾的自然语言结果。

大段证据不在多个字段重复传输。主 Tool 返回精简摘录；详细内容通过 `get_evidence` 或可选 Resource URI 读取。

## 17. 外部与内部 LLM 边界

外部 Agent 与后端 Agent 不共享隐式会话。

外部 Agent 调用时提供显式任务上下文：

- 查询。
- 项目作用域。
- 当前文件、符号或需求片段。
- 当前工作阶段。
- 可选响应档位。

服务端不要求或读取外部 Agent 的完整隐藏对话。

后端使用 Model Gateway 和能力路由层，不绑定具体 LLM 供应商。能力维度包括：

- 结构化输出。
- 复杂推理。
- 长上下文。
- 成本。
- 延迟。
- 超时与降级能力。

OpenAI-compatible 或 Anthropic-compatible 仅作为供应商适配协议，不能替代内部统一能力契约。

## 18. 模型部署

### 18.1 Provider 类型

- Local CPU Provider。
- Local GPU Provider。
- Remote API Provider。

Embedding、Reranker 和 LLM 可以分别选择不同 Provider。

### 18.2 本地默认模型

- Embedding：`BAAI/bge-m3`。
- Reranker：`BAAI/bge-reranker-v2-m3`。

BGE-M3 默认只提供 Dense Embedding。Sparse/BM25 由 Qdrant 负责。

### 18.3 增强模型

GPU或云端环境允许显式选择 Qwen3 Embedding/Reranker 增强档。切换 Embedding 模型时必须创建新索引版本并重新向量化。

### 18.4 DeepSeek V4-Flash

DeepSeek V4-Flash 用于后端 Agent 和复杂语义判断。它不是 Embedding 模型，也不是主 Reranker。当前 DeepSeek API 没有作为本系统基线依赖的原生 Embedding 或 Rerank Endpoint。

### 18.5 本地性能原则

- 入库向量化使用异步批处理。
- 在线查询优先于批量入库任务。
- Rerank 只处理融合后的有限候选。
- Embedding 与 Reranker 可以按需加载。
- CPU 模式允许使用 ONNX/OpenVINO 或量化实现。
- 建议本地基线为现代 8 核 CPU 与 16GB RAM；更高配置用于改善批量入库和 Rerank 延迟。

## 19. 延迟与降级

本系统不追求亚秒级检索。需求、设计和编码辅助场景可以接受几十秒级高质量检索。

三个 Agent 均保留，不因理论超时提前合并。实际优化依据 ChatGPT App、Claude Code 与 DeepSeek Harness 的真实评测。

每个目标 Host 使用独立的超时配置：

- ChatGPT App 使用宿主提供的 MCP Tool 超时策略。
- Claude Code 使用其 MCP Tool 超时配置。
- DeepSeek Harness 使用 `toolCallTimeoutMs`。
- 服务端节点超时和总超时必须小于目标 Host 配置。

当部分检索路径超时但已有可靠证据时返回 `partial`。当系统无法形成可靠证据时返回 `no_evidence` 或 `failed`。

超时数值由目标部署环境的 P50/P95 评测确定，并作为运行配置管理，而不是写死在协议契约中。

## 20. 运行状态保留

- 知识源、Chunk、向量和图关系跟随知识库生命周期保存。
- Agent 运行状态和追踪记录使用 TTL。
- 首期不实现广义敏感内容脱敏；凭据值仍按第 7 节执行专项规范化。
- 追踪配置必须允许关闭查询正文和证据正文记录，只保留 ID、状态、耗时和错误。
- Agent 推理结果不自动写回项目知识库。

## 21. 实例与并发模型

### 21.1 并发请求

同一后端服务支持多个 ChatGPT App、Claude Code、DeepSeek Harness 和同一 Agent 的多个会话并发访问：

- 不保存全局活动项目或隐式会话状态。
- 每个请求独立携带 `project_scope`。
- LangGraph 状态按 `request_id` 和 `run_id` 隔离。
- PostgreSQL、Qdrant 和模型客户端使用连接池。
- LLM、Embedding 与 Reranker 使用独立并发上限。

### 21.2 单写多读部署

首期支持两种实例模式：

- `writer`：唯一知识库维护实例，提供 Web 管理端、REST 管理 API、入库任务、索引发布、数据库迁移和只读 MCP 检索。
- `reader`：只提供只读 MCP 检索，连接共享的 Qdrant 与 PostgreSQL。

Writer 通过可替换的 `WriteCoordinator` 获得写入所有权。首期使用 PostgreSQL 单 Writer 租约，误启动第二个 Writer 时拒绝进入写模式。

Reader 所需的 Chunk 正文、父级上下文和来源定位必须位于共享数据库中，`get_evidence` 不依赖访问 Writer 本地原始文件。

单写多读只是首期部署策略，不是永久架构限制：

- 写入协调逻辑通过 `WriteCoordinator` 抽象。
- 原始文件存储通过 `SourceObjectStore` 抽象。
- 首期使用本地文件系统 Provider。
- 后续可以切换 S3 兼容对象存储和分布式任务协调器。
- 数据模型、索引版本和 MCP 契约不得依赖永远只有一个 Writer。

## 22. 模块化契约

建议共享契约目录至少包含：

- `common.schema.json`
- `retrieval-plan.schema.json`
- `evidence-ledger.schema.json`
- `evidence-assessment.schema.json`
- `context-package.schema.json`
- `mcp-search-input.schema.json`
- `mcp-search-output.schema.json`
- `mcp-get-evidence.schema.json`

公共定义复用知识域 ID、项目 ID、知识源 ID、证据 ID、索引能力、版本、状态和来源定位。节点专属 Schema 只描述本节点输入输出。

内部 Agent Schema 不直接复用 MCP 对外响应 Schema。

1. **001 Minimum RAG MCP Loop**
   - React 管理页与 REST 管理 API。

   - Markdown 与 Java 上传、凭据值规范化和结构切片。
   - BGE-M3 Dense 索引。
   - 确定性证据装箱。
   - `search_knowledge` 与 `get_evidence`。
   - ChatGPT App、Claude Code、DeepSeek Harness 和基础评测闭环。
2. **002 Hybrid Retrieval Precision**
   - Qdrant BM25/Sparse、融合和 BGE Reranker。
   - 与 001 Dense 基线进行质量和延迟对照。
3. **003 Structured Asset Expansion**
   - Word、PDF、OpenAPI、DDL、Go、Python 等格式按独立验收批次扩展。
4. **004 Graph RAG**
   - PostgreSQL 图关系、硬关系、软关系和有限跳扩展。
   - 与混合检索基线进行对照。
5. **005 Agentic Retrieval Orchestration**
   - 三 Agent、追加式证据账本、补充检索和上下文编排。
   - 与确定性检索基线进行对照。
6. **006 Runtime Hardening**
   - 单写多读实例、Provider 配置、追踪、运行指标和演进接口。

总蓝图描述完整目标架构，但每个 Feature 必须能够独立验收。

## 24. 评估策略

### 24.1 离线检索评估

- Recall@K。
- MRR。
- nDCG。
- 证据来源覆盖率。
- 冲突识别准确率。
- 项目作用域过滤正确率。
- 跨项目串库次数，目标必须为零。

### 24.2 硬性验收指标

- 跨项目串库次数必须为零。
- MCP Schema 合法率在验收测试集中必须为 100%。
- 返回证据来源可定位率在验收测试集中必须为 100%。

### 24.3 基线对照指标

首个闭环建立 Recall@K、MRR、nDCG、P50/P95 延迟和模型成本基线。后续 Feature 在进入 `plan.md` 前，必须在 `research.md` 中声明相对基线目标。

BM25、Rerank、Graph 和三 Agent 等增强只有在固定评测集上证明收益且未违反硬性指标时，才能进入默认检索路径。

### 24.4 目标 Host 真实任务评估

在 ChatGPT App、Claude Code 与 DeepSeek Harness 中分别执行：

- 基于老系统生成需求说明。
- 根据现有接口形成详细设计。
- 修改与既有模块一致的代码。
- 生成针对既有行为的测试用例。

对比无 RAG 与启用 RAG 时：

- 项目事实准确度。
- 来源可追溯性。
- 错误 API、表、类和配置引用数量。
- 用户修正次数。
- Tool 调用成功率。
- P50/P95 延迟。
- 模型调用成本。

评估用于系统验收与优化，不在运行时对外部 Agent 产物执行门禁。

## 25. 首期成功条件

首期端到端闭环满足以下条件：

- 用户可以通过 Web 管理端创建知识库，并上传 Markdown 文档和 Java 源代码。
- 入库状态和失败原因可见。
- ChatGPT App、Claude Code 与 DeepSeek Harness 均能调用 `search_knowledge`。
- 外部 Agent 能获得带来源定位的核心证据。
- 外部 Agent 能通过 `get_evidence` 展开详细内容。
- 多项目并行使用时不发生隐式活动项目污染。
- 公共知识与项目知识能够区分来源。
- 凭据值不会进入检索索引或 MCP 证据正文，字段名和配置结构仍可检索。
- 相同评测集可重复执行并比较检索质量。
- 系统不依赖 Neo4j、MCP Resources 或 MCP Tasks 才能完成核心流程。

## 26. 后续演进触发条件

以下能力仅在满足触发条件后进入新的 Feature：

- **自动内容同步**：手动维护已成为主要使用障碍。
- **Neo4j**：PostgreSQL 一至三跳图查询无法满足质量或性能要求。
- **MCP Tasks**：目标客户端稳定支持，且存在真实分钟级在线检索任务。
- **认证**：服务需要监听非本机地址或由多个用户访问。
- **敏感内容脱敏**：知识源或追踪日志进入受监管环境。
- **更强 Embedding/Reranker**：评测证明 BGE 基线无法满足代码或跨语言检索目标。

这些触发条件是架构演进门槛，不是当前规格中的未决占位。
